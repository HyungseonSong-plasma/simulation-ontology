# ADR-0030 — SOL v0.1 Design-Stage Closure

**Status:** Accepted  
**Date:** 2026-08-20  
**Scope:** SOL v0.1 design-stage closure  
**Depends on:** ADR-0001..0029 and accepted Thermal + Plasma/QRC reference-validation artifacts

## Context

SOL v0.1 began as a solver-independent simulation ontology architecture and progressed through focused design, independent counterexample validation, machine-readable consolidation, canonical package/model boundaries, and reference-model stress tests.

The design-stage closure criteria require more than an architecture diagram. The accepted baseline must provide:

1. stable semantic boundaries and explicit ownership of unresolved/post-design concerns;
2. machine-readable focused representations for the accepted language contracts required by the v0.1 design scope;
3. deterministic independent validation for the same normalized inputs;
4. successful minimal reference cases that exercise materially different semantic dimensions;
5. no obvious contradiction against the official reference backends used as design sanity checks;
6. durable repository state that a new Operating Desk context can recover without relying on hidden chat history.

The final independent audit initially returned `Revise` only for documentation/machine-registry transcription drift. Those findings were remediated and the focused closure readback returned **Accept**.

## Decision

**SOL v0.1 DESIGN-STAGE IS CLOSED.**

The closed design-stage baseline consists of:

- ADR-0001 through ADR-0030;
- Core architecture frozen through ADR-0017;
- focused Constraint/Interface/Value/Unit/Dimension/ValueDefinition language and schema consolidation through ADR-0027;
- canonical normalized ontology-package/resource integration from ADR-0028;
- closed ResolvedModelSnapshot reference-validation boundary from ADR-0029;
- accepted Minimal Thermal reference-model validation;
- accepted Minimal Plasma/QRC reference-model validation;
- final independent design-stage closure readback.

Closure means the v0.1 architecture/language/package/reference-model design has a coherent, independently validated baseline suitable for subsequent implementation and integration work.

Closure **does not mean** production backend adapters, runtime execution, UI/application syntax, or all future domain ontologies are complete.

## Accepted closure evidence

### Core semantic architecture

The baseline preserves:

- SimulationModel / Analysis / SimulationTask / SolverConfiguration separation;
- explicit Simulation/Model/Task bindings;
- direct non-transitive model-component membership;
- explicit semantic inter-model relations;
- first-class spatial Scope;
- backend independence;
- explicit taxonomy and Interface composition;
- Constraint authority for cardinality.

### Constraint/language contracts

All six minimum Constraint families have accepted focused machine-readable and semantic-validation boundaries:

```text
Cardinality / QRC
Type
Value
Dimension
Compatibility
Conditional
```

Interface, Value/Unit/Dimension, ValueDefinition, canonical identity/package, and resolved-model-snapshot boundaries are likewise accepted.

### Minimal Thermal reference gate

**PASS**

The Thermal case exercises:

- Simulation / SimulationModel / SimulationTask / StationaryAnalysis;
- model-component and inter-model relations;
- BoundaryCondition targeting;
- PropertyDefinition assignments;
- Value and UnitReference;
- Interface-targeted Dimension Constraints;
- metrology PASS / INDETERMINATE / mismatch behavior.

### Minimal Plasma/QRC reference gate

**PASS**

The Plasma case exercises:

- Reaction/Species specialization;
- explicit `reactants` and `products` relations;
- Interface relation mapping;
- multiple independent QRC obligations over one relation;
- closed-snapshot, distinct-identity, subtype-qualified counting;
- missing, extra, wrong-type, duplicate, unresolved, invalid-interval, open-snapshot, and order-permutation counterexamples.

### Cross-backend/reference sanity

Official MOOSE, COMSOL, and Ansys documentation used throughout design-stage validation reveals no obvious counterexample requiring reopening the frozen Core architecture. Palantir Interface/Ontology concepts remain compatible as conceptual evidence for explicit reusable capability contracts and mappings.

## Reopen criteria

SOL v0.1 design-stage closure SHALL be reopened only when new evidence demonstrates at least one of:

1. a genuine Core architecture defect;
2. a normative contradiction among accepted v0.1 contracts;
3. independent-validator nondeterminism for the same normalized input;
4. a cross-backend semantic counterexample showing the solver-independent contract is unsound;
5. a required reference-model semantic impossibility that cannot reasonably be classified as a domain/Profile/Adapter/backend limitation or explicitly deferred feature.

A reopen must be narrow, evidence-backed, and recorded through a new focused decision/validation cycle.

## Non-reopen triggers

The following do **not** by themselves reopen the v0.1 design-stage baseline:

- MOOSE/COMSOL/Ansys installation availability;
- proprietary license availability;
- backend runtime/API availability;
- repository checkout, DNS, connector, or execution-environment interruption;
- absence of a production BackendAdapter;
- incomplete UI/application tooling;
- future implementation optimization;
- desire for richer domain taxonomy when the existing Core remains semantically valid.

These belong to operational, implementation, Adapter/integration, or future-version work unless they produce a genuine semantic counterexample.

## Explicit post-design work

The next project stage may include, without reopening ADR-0030 by default:

- production TypeScript-oriented SDK/compiler implementation;
- Profile and BackendAdapter authoring/implementation;
- MOOSE/COMSOL/Ansys integration and executable V&V;
- richer thermal/plasma/domain ontology packages;
- additional reference cases;
- application/UI model-document authoring;
- CI packaging and release engineering;
- namespace federation or multi-model/co-simulation only if separately justified.

## Durable-state rule

GitHub artifacts are the Source of Truth for recovery. A resumed Operating Desk should reconstruct the project state from:

1. repository README/status;
2. ADR-0030 and prior ADRs;
3. current Architecture and Ontology Language documents;
4. machine-readable schema/Core registries;
5. accepted final Validation and reference artifacts.

Chat history is working context, not the authoritative closure record.

## Consequence

The Simulation Ontology project may now transition from **design-stage ontology/language architecture** to **post-design implementation, Adapter integration, and executable V&V** while preserving the v0.1 semantic baseline as the contract against which those implementations are judged.
