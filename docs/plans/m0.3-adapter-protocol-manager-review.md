## 2. Accepted decisions

### 2.1 MappingPlan semantics versus backend execution scheduling

Core owns:

- MappingPlan DAG semantics;
- dependency/prerequisite semantics;
- canonical deterministic ordering used for representation, comparison, and reproducible output.

Adapter owns backend execution scheduling for the whole validated plan.

An adapter MAY execute independent actions in a different valid topological order or in parallel, provided all canonical dependency semantics are preserved and the realization report makes execution outcomes/evidence observable.

Therefore:

```text
canonical deterministic order != mandatory physical backend total order
```

### 2.2 Dual compatibility gate

Adapter interoperability requires compatibility on both independently versioned semantic surfaces used across the boundary:

```text
Adapter Protocol compatibility
AND
Public Contract compatibility
```

A matching Adapter Protocol version alone is insufficient when the peers cannot interpret the Public Contract version used by shared canonical payloads.

Adapter implementation/package versions remain independent and never imply either compatibility result.

### 2.3 Bootstrap negotiation must be version-safe

Protocol 0.1 must define a minimal, forward-safe bootstrap/description shape sufficient to discover at least:

- adapter identity/version;
- supported Adapter Protocol range;
- supported Public Contract range/version set;
- declared capabilities/target evidence needed before execution.

The bootstrap cannot require the caller to already know an incompatible full protocol payload interpretation in order to discover compatibility.

This does not create an additional semantic version axis; it is part of the Adapter Protocol compatibility design.

### 2.4 `validate_plan` is advisory; `execute_plan` is authoritative

`validate_plan` is a deterministic preflight assessment against the state/evidence available at validation time. It is not a durable authorization token guaranteeing later execution.

`execute_plan` is the authoritative operation boundary and SHALL re-check all execution-critical compatibility, plan identity/integrity, and current preconditions needed to prevent a validate-then-execute TOCTOU assumption.

Protocol 0.1 does not require a persistent acceptance-token/state-machine design unless later evidence justifies it.

### 2.5 Idempotency and retry boundary

`validate_plan` SHOULD be idempotent for the same canonical input and declared relevant state/evidence.

`execute_plan` MUST NOT be assumed idempotent unless an adapter/operation explicitly guarantees that property.

Automatic retry policy, transport reconnect behavior, timeout/backoff, and request replay mechanics are deferred to M0.5 transport work. M0.5 SHALL NOT blindly retry `execute_plan` after an ambiguous response-loss/failure boundary.

### 2.6 Backend-native data boundary

Backend-native object models, vendor API types, and solver-native structures SHALL NOT become canonical semantic payloads or semantic identity.

Opaque backend artifact references MAY cross the boundary as provenance/evidence metadata when useful, for example a backend job/artifact handle. Such references:

- must remain opaque to Core semantics;
- must not define canonical identity/equality;
- must not be required to understand solver-independent meaning;
- may be used for traceability, evidence, diagnostics, or later backend-specific retrieval.

Therefore:

```text
backend-native semantic object/type  -> forbidden as canonical semantics
opaque backend artifact reference    -> permitted as provenance/evidence
```

### 2.7 Capability stability for Protocol 0.1

For Protocol 0.1, capabilities advertised in an adapter description are treated as stable for the lifetime/scope of that description unless the contract explicitly says otherwise.

Transient environment/backend availability changes are handled by `validate_plan` and authoritative `execute_plan` precondition checks rather than introducing a general capability-event/state-machine in Protocol 0.1.

A richer dynamic-capability model is deferred until implementation evidence requires it.

### 2.8 Published baseline terminology

M0.3 should produce a **published, versioned Adapter Protocol 0.1 baseline**, not claim mature long-term stability before real-adapter feedback exists.

Once published, however, Protocol 0.1 semantics SHALL NOT be silently redefined. Incompatible MOOSE or later adapter feedback requires an explicit new protocol version boundary.

## 3. Operation-surface decision

Protocol responsibilities do not imply one remote method per responsibility.

The initial operation surface remains intentionally minimal around the following candidates:

```text
describe_adapter
validate_plan
execute_plan
```

Exact names/payload schemas remain M0.3 work.

The following are responsibilities or Core/adapter-local operations rather than automatically separate public protocol calls:

- Core-side BackendTarget selection/resolution from adapter description/evidence;
- capability interpretation from adapter description;
- adapter-internal backend realization normalization;
- Core-side RealizationEffect semantic comparison/classification;
- realization reporting, which may be returned as part of execution results instead of requiring a standalone remote call.

Phase 0 must justify any additional public operation independently rather than serializing the existing Rust trait surface or the older conceptual responsibility list one-to-one.

## 4. Protocol error and semantic lifecycle boundary

The following categories remain distinct:

```text
protocol compatibility / bootstrap failure
request-contract failure
operational execution failure
canonical semantic outcome returned successfully
```

Raw protocol/request/operational errors are not themselves:

```text
PASS
FAIL
BLOCKED
INDETERMINATE
```

Only an appropriate successful canonical semantic outcome/evidence may subsequently be interpreted/classified by Core under the existing SOL evaluation lifecycle.

This review therefore supersedes any generic policy wording that would directly map a raw missing/unknown Adapter Protocol compatibility result to `BLOCKED` without a canonical semantic outcome.

## 5. Validator counterexamples accepted as required coverage

M0.3 fixtures/tests should cover at least the following cases.

### Alternative valid scheduling

```text
DAG: A and B independent
canonical representation order: A, B
backend executes: B, A
```

Expected: valid if dependency semantics and required reporting are preserved.

### Dual-version mismatch

```text
Protocol 0.1: compatible
Public Contract: incompatible
```

Expected: execution does not proceed.

### Bootstrap paradox

A caller that does not yet know the adapter's supported full protocol version must still be able to obtain enough version information to reject incompatibility deterministically.

### Validate/execute TOCTOU

```text
validate plan A
state/plan/precondition changes
execute later
```

Expected: `execute_plan` re-checks authoritative execution conditions; prior validation is not blindly trusted.

### Ambiguous execution retry

```text
execute_plan causes backend side effect
response is lost
caller cannot prove whether execution completed
```

Expected: no protocol-level assumption that repeating `execute_plan` is safe/idempotent.

### Opaque provenance versus semantic leakage

Opaque backend job/artifact reference used only for evidence: permitted.

Solver-native object structure used as canonical semantic identity/payload: rejected.

### Error/lifecycle separation

```text
unsupported protocol version -> FAIL
malformed request             -> BLOCKED
```

Both mappings are invalid.

## 6. Rejected or deferred alternatives

### Rejected: canonical order as mandatory backend total order

Reason: over-constrains valid backend scheduling/parallelization. DAG dependencies are semantic; canonical deterministic order is required for representation/reproducibility but need not be the physical execution schedule for independent actions.

### Rejected: one protocol method per conceptual responsibility

Reason: leaks implementation decomposition into the public interoperability surface and creates unnecessary long-term compatibility cost.

### Rejected: `validate_plan` as durable execution authorization

Reason: creates state/TOCTOU complexity without current evidence. Preflight plus authoritative execution re-check is simpler for Protocol 0.1.

### Rejected: `execute_plan` idempotent by default

Reason: real solver/backends commonly produce side effects; retry safety must be explicit rather than assumed.

### Rejected: all backend references forbidden

Reason: opaque provenance/evidence references are useful and do not violate solver-independent semantics when equality/meaning do not depend on them.

### Deferred: general dynamic capability/event model

Reason: Protocol 0.1 can treat description capabilities as stable within descriptor scope and use validate/execute preconditions for transient state. Revisit from real-adapter evidence.

### Deferred: transport retry/reconnection semantics

Reason: belongs to M0.5 after protocol semantics are fixed.

## 7. Required updates to planned M0.3 phases

The existing #39–#44 phase structure remains valid; no new Phase is required.

- #39: distinguish canonical DAG/order from backend scheduling; classify opaque backend references versus semantic leakage.
- #40: add Protocol + Public Contract dual compatibility, bootstrap negotiation, and Protocol 0.1 capability-stability rule.
- #41: define `validate_plan` as advisory preflight rather than durable authorization.
- #42: make `execute_plan` authoritative for execution preconditions; permit dependency-preserving alternative scheduling/parallelism; define opaque provenance reporting.
- #43: define `validate_plan` idempotency expectation and `execute_plan` non-idempotent-by-default rule; prohibit blind retry assumptions.
- #44: add canonical Protocol JSON Schema plus regression fixtures for all counterexamples above and use published-versioned-baseline terminology.
