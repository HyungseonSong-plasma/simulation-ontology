## Objective

Publish a solver-independent realization payload that allows an external real adapter to construct a deterministic backend model from canonical SOL information without deriving physics from MappingPlan action IDs, opaque extensions, private Core state, or backend-native semantic objects.

## Compatibility rule

0.1 is frozen. 0.2 is explicit.

```text
Protocol 0.1 + Public Contract 0.1
  remains valid for existing 0.1 consumers

Protocol 0.2 + Public Contract 0.2
  required for the explicit RealizationSpec path
```

No adapter package version implies either compatibility pair.

## Public Contract 0.2 realization subset

The initial implementation publishes the top-level documents required at the adapter realization boundary:

- `MappingPlanDtoV02`
- `BackendTargetDtoV02`
- `RealizationSpecDtoV02`

The existing Public Contract 0.1 model/validation/evaluation surfaces remain available and unchanged. M0.8 does not require a wholesale model-document migration merely to resolve #110.

### RealizationSpec contents

The 0.2 RealizationSpec carries:

- `public_contract_version = "0.2"`;
- `ontology_version`;
- `source_model` canonical reference;
- canonical realization entities (`id`, `kind`, `semantic_type`);
- explicit scalar parameter bindings (`semantic_parameter`, numeric value, canonical unit reference);
- canonical `SpatialScope` projections;
- canonical semantic relations;
- exactly one action binding per MappingPlan action, referencing explicit subjects/scopes.

All collections use deterministic canonical ordering. Duplicate identities and unresolved references are semantic errors.

### Initial quantity boundary

M0.8 deliberately supports scalar JSON-number quantities only. Vectors/tensors/functions/tables and a complete dimensional-conversion algebra are deferred. This is sufficient for the first steady heat-conduction vertical slice while keeping the contract explicit and testable.

## Protocol 0.2 request rule

Both operations carry the same full realization input:

```text
validate_plan(target, plan, realization_spec)
execute_plan(target, plan, realization_spec)
```

The plan and spec are re-sent at execute time. Validation does not mint an authorization token. Execute remains non-idempotent by default and ambiguous response loss does not authorize replay.

## Thermal proof target

The positive fixture must explicitly expose at least:

- temperature Field;
- steady heat Equation;
- Fourier ClosureRelation;
- thermal conductivity with numeric value and unit;
- 1D spatial domain size and boundary location;
- main-domain and hot-wall SpatialScopes;
- Dirichlet temperature condition with numeric value and unit;
- StationaryAnalysis;
- maximum-temperature ObservationModel;
- action bindings connecting the three existing thermal plan actions to those canonical subjects/scopes.

A second fixture must keep exactly the same plan but change at least conductivity and boundary temperature. The canonical RealizationSpec must differ.

## Negative cases

M0.8 must reject or classify as non-conforming:

- missing action binding;
- unknown action binding;
- duplicate action binding;
- unresolved bound subject;
- unresolved bound scope;
- duplicate realization entity or scope identity;
- malformed unit reference;
- backend-native object/identity leakage;
- known PlanAction extension attempts to carry realization/physics meaning;
- Protocol 0.2 request missing `realization_spec`;
- mixed Public Contract 0.1/0.2 target/plan/spec;
- Protocol 0.1 request reinterpreted as carrying 0.2 meaning.

## Conformance boundary

Protocol/Public Contract conformance proves structural and semantic interoperability only. It does not prove MOOSE installation correctness, MOOSE object choice, mesh correctness, convergence, or physical/numerical accuracy.

The MOOSE adapter owns backend-native typed IR, deterministic `.i` generation, exact executable support, backend process/workspace/artifact capture, regression tests, and physical/numerical V&V.

## MOOSE handoff gate

Phase 4 may unblock MOOSE canonical mapping only when:

- Public Contract 0.2 RealizationSpec is merged on SOL `main`;
- Adapter Protocol 0.2 request boundary is merged;
- positive thermal fixture and negative/distinguishability cases are merged;
- 0.2 schema/conformance gates are green;
- exact compatibility declarations are documented;
- #110 records merge/main evidence.

The handoff must identify the exact SOL files/fixtures the MOOSE Team should consume and must not require access to private SOL repository state at runtime.

## Exit condition

M0.8 reaches the exit gate at #129. The milestone closes only after independent Validator review confirms:

- 0.1 is unchanged;
- 0.2 supplies sufficient explicit realization information;
- action IDs/extensions remain non-semantic;
- backend-native identity does not leak;
- version negotiation is explicit;
- same-plan/different-spec distinguishability is executable;
- conformance remains distinct from backend V&V.
