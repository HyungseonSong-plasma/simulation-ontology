# M0.9 Adapter Runtime 0.2 Integration Plan

**Status:** Accepted and in implementation  
**Date:** 2026-08-23  
**Parent tracker:** #141  
**Prerequisites:** M0.7 and M0.8 accepted complete

## Purpose

M0.9 connects the already-published Public Contract 0.2 / Adapter Protocol 0.2 `RealizationSpec` boundary to the accepted M0.7 solver-neutral Adapter Runtime.

M0.9 is an integration milestone, not a new semantic-contract milestone. It must not redefine Public Contract 0.2, Adapter Protocol 0.2, `MappingPlan`, or `RealizationSpec` meaning.

## Accepted architecture

```text
0.1 path
Public Contract 0.1 + Adapter Protocol 0.1
        -> existing M0.7 runtime behavior, unchanged

0.2 path
Public Contract 0.2 + Adapter Protocol 0.2 + RealizationSpec
        -> explicit runtime contract profile
        -> live compatibility/capability evidence
        -> solver-neutral projection / deterministic selection
        -> version-correct validate / execute dispatch
```

Runtime routes canonical payloads. It does not interpret, infer, or synthesize physics/realization semantics.

## Phase structure

- Phase 0 — #142 Runtime 0.2 Profile & Version Routing Boundary
- Phase 1 — #143 Live 0.2 Compatibility & Capability Projection
- Phase 2 — #144 RealizationSpec-aware Validate & Execute Dispatch
- Phase 3 — #145 Selection, Mixed-Version & 0.1 Regression Matrix
- Phase 4 — #146 External Adapter 0.2 Runtime Integration & Milestone Gate

## Cross-version invariants

- `(Adapter Protocol 0.1, Public Contract 0.1)` remains the existing runtime pair.
- `(Adapter Protocol 0.2, Public Contract 0.2)` is an explicit realization runtime pair.
- mixed pairs are not implicitly supported;
- DTO/schema presence alone does not establish runtime support;
- live `describe_adapter` evidence establishes compatibility, not registration/package metadata;
- no hidden fallback from a 0.2 realization request to the 0.1 path;
- zero/one/multiple eligible adapter outcomes remain deterministic;
- `validate_plan` remains advisory and side-effect free;
- `execute_plan` remains authoritative and non-idempotent by default;
- ambiguous execute response loss grants no automatic replay authority.

## Solver-neutral boundary

M0.9 does not add solver-native mapping, backend object identity, or solver runtime dependencies to Core. Passing M0.9 runtime integration/conformance is not physical or numerical V&V.

## Exit rule

Phase 4 is the milestone exit gate. It requires exact-head CI, external-process 0.2 end-to-end evidence, independent 0.1 regression evidence, Validator audit, explicit milestone-exit decision, final merge, and `main` verification.

GitHub Milestone UI state is administrative. Canonical progress is Phase issues #142–#146 plus parent #141 and exact repository evidence.
