# M0.7 Adapter Runtime & Registry Plan

**Status:** Accepted and in implementation  
**Date:** 2026-08-22  
**Parent tracker:** #111

## Purpose

M0.7 turns the already-published adapter protocol/transport/conformance foundations into a solver-neutral Core runtime that can explicitly register external adapter commands, manage live sessions, obtain compatibility/capability evidence, and select an eligible adapter for a canonical backend target.

The milestone is intentionally smaller than a complete plugin ecosystem. Its goal is to establish the runtime boundary required by future SDK/GUI work without stabilizing package discovery, marketplace, signing, auto-update, or solver-specific integration inside Core.

## Accepted context

The prerequisite sequence is complete:

```text
M0.2 Public Contract 0.1
   -> M0.3 Adapter Protocol 0.1
   -> M0.4 MockAdapter conformance
   -> M0.5 JSON-RPC / stdio transport
   -> M0.6 external-adapter conformance tooling
   -> M0.7 Adapter Runtime & Registry
```

M0.6 is accepted complete and its post-completion documentation synchronization is merged on `main`.

The independent real-adapter track may proceed in parallel. M0.7 does not own MOOSE-native realization, solver installation, solver regression, or physical/numerical V&V.

## Core architecture

The milestone preserves three different kinds of state:

```text
canonical semantic state
        |
        v
BackendTarget

local platform/runtime state
        |
        v
AdapterRegistration

live operational state
        |
        v
AdapterInstance / process session
```

These MUST NOT be collapsed.

The intended runtime path is:

```text
Simulation / MappingPlan
        |
        v
canonical BackendTarget requirements
        |
        v
Adapter Runtime / Registry
        |
        +-> explicit local registrations
        |
        +-> launch/bootstrap external adapter process
        |
        +-> describe_adapter compatibility/capability evidence
        |
        +-> deterministic eligible-adapter selection
        |
        v
selected live adapter instance
        |
        v
validate_plan / execute_plan
```

## Product boundary

### M0.7 owns

- Core-local adapter registration model;
- explicit local registration lifecycle;
- composition of registered commands with the accepted M0.5 subprocess/session transport;
- live `describe_adapter` inspection;
- dual Adapter Protocol/Public Contract compatibility evaluation;
- solver-neutral target/capability evidence projection;
- deterministic eligible-adapter selection;
- external-command integration evidence;
- runtime architecture/counterexample coverage.

### M0.7 does not own

- canonical ontology changes for a specific solver;
- Adapter Protocol 0.1/Public Contract 0.1 semantic changes;
- MOOSE/COMSOL/Ansys runtime dependencies in Core;
- solver-native mapping tables;
- backend physical/numerical validation;
- remote/network transport;
- automatic adapter discovery;
- stable adapter package/manifest format;
- marketplace/download/install/signing/auto-update;
- stable GUI plugin UX;
- stable TypeScript/Python SDK surface.

Exact local registration persistence, CLI spelling, environment variables, and future GUI packaging remain Experimental unless separately stabilized.

## Phase structure

### Phase 0 — Runtime Boundary & Registration Model — #112 — COMPLETE

Establish executable Core-local types and architecture tests for the accepted distinction:

```text
BackendTarget != AdapterRegistration != AdapterInstance
```

Accepted implementation adds the Core-local `sol-adapter-runtime` boundary and executable counterexamples while keeping runtime/process identity outside canonical semantics.

Primary gates:

- runtime data cannot define canonical semantic identity;
- static registration cannot claim trusted compatibility/capability truth;
- no solver-specific dependency or native object identity enters Core;
- architecture counterexamples are executable.

### Phase 1 — Explicit Local Adapter Registration — #113 — COMPLETE

Implement the minimum deterministic local registry needed to locate external adapter commands.

Accepted implementation provides explicit register/get/list/remove/enable-disable behavior, deterministic registration-ID ordering, duplicate rejection, and local-only invocation configuration without persistence or interoperability claims.

Primary gates:

- explicit add/read/list/remove/enable-disable behavior;
- deterministic duplicate/conflict behavior;
- minimum invocation configuration only;
- persistence/config/CLI details remain Experimental;
- no discovery/marketplace/package standardization.

### Phase 2 — Adapter Process & Session Lifecycle — #114 — ACTIVE

Compose registration with the accepted M0.5 process transport/session lifecycle.

Primary gates:

- registered command launch;
- mandatory description/bootstrap before typed use;
- explicit close/reconnect/new-session behavior;
- typed transport/process failure separation;
- no automatic replay after ambiguous `execute_plan` response loss;
- existing M0.5 parity semantics preserved.

Implementation work currently exists on PR #122. It remains non-accepted until exact-head CI and merge/main verification satisfy normal Phase gates.

### Phase 3 — Compatibility & Capability Discovery — #115

Use live `AdapterDescription` as runtime interoperability evidence.

Primary gates:

- independent Adapter Protocol/Public Contract compatibility evaluation;
- target/capability declaration taken from protocol bootstrap evidence;
- package version proves neither compatibility axis;
- missing or contradictory live evidence cannot be overridden by registration hints;
- compatibility outcomes remain separate from SOL lifecycle classification.

### Phase 4 — Adapter Selection & Solver-neutral Projection — #116

Provide deterministic Core selection/projection for future CLI/SDK/GUI consumers.

Primary gates:

- selection based on canonical target requirements plus live compatibility/capability evidence;
- deterministic zero/one/multiple-candidate behavior;
- no solver-specific semantic branch in generic selection logic;
- local registration/session identity remains non-semantic;
- exact GUI and stable SDK APIs remain outside the milestone.

### Phase 5 — External Adapter Runtime Integration & Milestone Gate — #117

Prove the complete runtime path against a standalone external adapter command and perform the milestone exit audit.

Primary gates:

- registration -> launch -> bootstrap -> compatibility/capability -> selection works end to end;
- selected live instance carries the existing Protocol operations;
- incompatible/not-established adapters are not silently treated as interoperable;
- failure/replay boundaries remain correct;
- required exact-head CI, architecture counterexamples, schema gates, and relevant conformance tests pass;
- independent Validator exit audit approves the exact candidate.

Phase 5 is the milestone exit gate and is not covered by bounded auto-merge while the Validator exit decision is pending.

## Compatibility policy

M0.7 introduces no new compatibility version axis.

The following remain independent:

- SOL Runtime Release;
- Public Contract version;
- Adapter Protocol version;
- ontology package version;
- external adapter implementation version.

The registry/runtime implementation does not infer compatibility from matching package versions or registration names.

A runtime/real-adapter finding that requires an incompatible Protocol/Public Contract semantic or structural change is a real gate. That path must return to Manager/Researcher/Validator review and use an explicit new version boundary rather than mutate 0.1 in place.

## Validation strategy

The milestone remains CI-first and counterexample-driven.

At minimum, the cumulative M0.7 suite must reject:

1. `BackendTarget` treated as a registration record;
2. `AdapterRegistration` treated as a live process/session;
3. path/PID/session/backend-native ID used as canonical semantic identity;
4. static registration compatibility overriding incompatible live description evidence;
5. automatic selection of an incompatible/not-established adapter;
6. nondeterministic hidden choice among multiple eligible adapters;
7. solver-specific branches defining generic Core runtime semantics;
8. solver runtime dependency leakage into Core;
9. transport/process failure relabeled as logical Protocol failure or SOL lifecycle state;
10. ambiguous execute-response loss authorizing automatic replay.

Positive integration must prove that an external process can be registered, bootstrapped, evaluated for dual compatibility/capabilities, selected, and used through the existing Protocol operations.

Protocol conformance remains distinct from backend physical/numerical correctness.

## Relationship to the MOOSE adapter track

The external MOOSE adapter is an independent project/team. Its responsibility is SOL-to-MOOSE realization, MOOSE execution/integration, backend regression, and physical/numerical V&V.

M0.7's responsibility is the generic Core runtime that can host/select an external adapter without knowing MOOSE-native semantics.

Cross-team rule:

```text
MOOSE implementation evidence
   -> demonstrates missing/contradictory SOL contract requirement
   -> durable handoff/evidence
   -> SOL Manager meeting
   -> accept / reject / version new Core contract change
```

MOOSE evidence is a real-system feedback source, not automatic semantic authority over SOL.

## Relationship to SDK and GUI work

The M0.6 roadmap allowed SDK and real-adapter work to proceed after the conformance foundation. The 2026-08-22 Manager decision selects M0.7 Adapter Runtime & Registry as the next Core milestone before stabilizing a broad TypeScript/Python SDK or GUI plugin surface.

Future GUI experience may present adapters as plugin-like selectable backends, but the implementation remains external-process based and solver-neutral.

A stable SDK/GUI surface should consume the runtime boundary after it has executable evidence rather than freeze incidental pre-M0.7 Rust/internal structures.
