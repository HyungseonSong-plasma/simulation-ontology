# M0.10 Canonical Simulation Run & Result Contract Plan

**Status:** Accepted; Phase 0 architecture decision recorded  
**Date:** 2026-08-23  
**Parent tracker:** #153  
**Architecture:** `docs/adr/ADR-005-canonical-run-result-boundary.md`  
**Prerequisites:** M0.9 accepted complete

## Purpose

M0.10 closes the solver-independent execution/result loop. SOL already routes canonical realization intent through the Adapter Runtime to external adapters. M0.10 adds the canonical boundary required to identify and transport scientific/numerical results without promoting solver-native result objects into Core semantics.

The intended product sequence is:

```text
SimulationModel / SimulationTask
  -> MappingPlan + RealizationSpec
  -> Adapter Runtime
  -> external solver adapter
  -> solver execution
  -> SimulationRunRecord
  -> ObservationResult
  -> later analysis / storage / SDK / application surfaces
```

M0.10 does not stabilize the SDK or GUI/application layer. Those surfaces should consume this milestone's accepted result semantics rather than define them implicitly.

## Accepted Phase 0 architecture

### Version boundary

Result semantics use:

```text
Public Contract 0.3
AND
Adapter Protocol 0.3
```

Public Contract 0.1/0.2 and Adapter Protocol 0.1/0.2 remain frozen in normative meaning. Public Contract 0.3 preserves the existing 0.2 `MappingPlan` / `RealizationSpec` separation while adding an explicit later run/result surface.

Result-capable adapter interoperability requires explicit support for both 0.3 axes; old adapters are not silently promoted or coerced.

### Semantic ownership

```text
ObservationModel
  -> canonical meaning of requested observation

SimulationRunRecord
  -> canonical operational record of one execution occurrence
  -> not a SimulationModel semantic entity
  -> not part of model semantic equality

ObservationResult
  -> scientific/numerical value actually produced for a requested observation

backend-native artifact/provenance
  -> opaque evidence only
  -> never canonical result identity
```

Execution success does not imply observation success. Every requested observation requires exactly one terminal outcome: produced result or typed non-production evidence/diagnostic.

### Result categories

Initial compact result support is scalar:

```text
ScalarObservationResult
  -> observation reference
  -> run reference
  -> value
  -> canonical unit
```

Distributed/field results use:

```text
DatasetObservationResult
  -> observation reference
  -> run reference
  -> canonical DatasetManifest
  -> solver-neutral DataReference
```

The concrete canonical field data format, content identity, and normalization rules are Phase 2 decisions. Backend files such as Exodus or vendor-native result objects may appear only as provenance and cannot replace the canonical dataset/result boundary.

## First vertical slice

Use the existing steady 1-D thermal realization case.

Required result evidence:

- `MaximumTemperature` as a compact scalar observation result;
- temperature field as a distributed dataset result;
- backend-native execution artifacts retained as opaque provenance;
- at least one negative case where execution succeeds but a requested observation is not produced.

This fixture is a semantic/protocol interoperability case. Physical/numerical correctness and solver-specific V&V remain adapter responsibilities.

## Cross-version invariants

- Public Contract 0.1 and Adapter Protocol 0.1 remain valid for their declared baseline.
- Public Contract 0.2 and Adapter Protocol 0.2 remain valid for the accepted RealizationSpec path.
- Public Contract 0.3 / Adapter Protocol 0.3 is the explicit run/result path.
- Supporting an older pair does not imply support for a newer pair.
- Runtime/adapter package version does not imply semantic/protocol compatibility.
- Existing execution response-loss behavior grants no replay authority.
- A native backend artifact cannot define canonical result identity/equality.
- Execution outcome and observation production remain distinct.

## Core vs adapter responsibility

Core owns:

- canonical run/result semantics;
- Public Contract 0.3 schemas/DTOs/normalization;
- Adapter Protocol 0.3 interoperability semantics;
- runtime routing/validation of the accepted result boundary;
- reusable conformance fixtures and tooling.

Real adapters own:

- mapping native solver outputs into accepted canonical result semantics;
- extraction of scalar observations;
- mapping fields/datasets into the accepted solver-neutral data boundary;
- backend-native artifact capture/provenance;
- solver-version compatibility;
- physical/numerical V&V.

## Resource-aware sequencing with the MOOSE adapter

The accepted project sequencing under limited concurrent-team capacity is:

```text
SOL M0.10 Phase 0
  -> record/merge architecture decision
  -> pause SOL implementation

MOOSE A0.1
  -> complete the existing 0.2 RealizationSpec -> MOOSE execution vertical slice

SOL M0.10 Phase 1 -> Phase 2 -> Phase 3
  -> publish/stabilize result contract/protocol surface

MOOSE follow-on result integration
  -> implement explicit Public Contract/Protocol 0.3 support

SOL M0.10 Phase 4 -> Phase 5
  -> real-adapter result vertical slice + exit
```

This sequencing avoids expanding MOOSE A0.1 scope retroactively and allows M0.10 result semantics to use real adapter evidence rather than speculative backend assumptions.
