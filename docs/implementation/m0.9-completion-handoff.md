## Accepted runtime capability

M0.9 integrates the already-published Public Contract 0.2 / Adapter Protocol 0.2 realization boundary into the solver-neutral Adapter Runtime while preserving the existing 0.1 path.

```text
Public Contract 0.1 + Adapter Protocol 0.1
        -> existing runtime profile

Public Contract 0.2 + Adapter Protocol 0.2 + RealizationSpec
        -> RuntimeContractProfile::realization_v02()
        -> live describe_adapter compatibility evidence
        -> target/capability projection
        -> profile-aware adapter selection
        -> typed validate_plan_v02 / execute_plan_v02
        -> external adapter process
```

The runtime routes canonical realization input; it does not interpret or invent realization semantics.

## Exit proof

The standalone external runtime consumer proves the complete 0.2 path through the public runtime API:

1. explicit local adapter registration;
2. external process launch and bootstrap;
3. live Protocol 0.2 / Public Contract 0.2 compatibility;
4. solver-neutral target/capability projection;
5. deterministic profile-aware selection;
6. Protocol 0.2 validation with full `target + plan + realization_spec`;
7. authoritative Protocol 0.2 execution with the same full realization input;
8. successful process shutdown;
9. deterministic repeated evidence output.

Negative evidence covers:

- 0.1-only adapters are not eligible for explicit 0.2 selection;
- multiple compatible 0.2 candidates remain `Ambiguous`;
- bootstrap/process failure remains a runtime/transport failure;
- execute response loss does not authorize transport replay;
- unsupported or mixed runtime contract profiles remain rejected by the accepted earlier phases;
- incompatible/unknown live compatibility is not promoted to compatibility.

## Preserved invariants

- Public Contract 0.1 and Adapter Protocol 0.1 semantics are unchanged.
- Public Contract 0.2 and Adapter Protocol 0.2 semantics are not redefined by runtime integration.
- `MappingPlan` remains orchestration identity/dependency structure; `RealizationSpec` remains separate canonical realization input.
- `validate_plan` remains advisory and side-effect free.
- `execute_plan` remains authoritative and non-idempotent by default.
- lost execute responses preserve no-replay authority and `MayHaveOccurred` semantics.
- `RuntimeContractProfile`, `BackendTarget`, `AdapterRegistration`, and `AdapterInstance` remain distinct runtime/platform concepts.
- Core remains solver-neutral and has no MOOSE/COMSOL/Ansys runtime dependency.

## Boundary of evidence

M0.9 completion establishes SOL runtime/protocol interoperability. It does **not** establish solver-native physical or numerical correctness, backend-specific mapping correctness, or solver V&V. Those remain adapter-team responsibilities.

## Next architectural boundary

A real backend adapter may now consume the published 0.2 realization contract through the accepted runtime boundary. Backend-specific translation from canonical `RealizationSpec` into solver-native IR/artifacts remains outside SOL Core.
