# M0.5 Transport and Process Error Propagation

**Status:** Phase 3 executable error profile
**Date:** 2026-08-22
**Milestone:** M0.5 — JSON-RPC / stdio Transport
**Parent tracker:** #74
**Phase:** #78
**Depends on:** Phase 2 #77 / PR #98

## Purpose

This profile makes malformed transport input and subprocess failure observable without redefining Adapter Protocol outcomes or SOL lifecycle state. It extends the Phase 2 session with stable caller-visible error categories and preserves process diagnostics as opaque evidence.

## Caller-visible evidence model

An operation can produce one of three disjoint channels:

1. typed Protocol success through `AdapterOperationResult::Success`;
2. a valid logical operation failure through `AdapterOperationResult::ProtocolFailure`;
3. a transport/session error through `AdapterSessionError` and its stable `AdapterSessionErrorKind`.

After a transport/session error the session is `Faulted`, so another operation cannot be submitted. Explicit `shutdown` then returns independent `AdapterProcessExit` evidence when the child can be reaped:

- `success`: operating-system exit success only;
- `code`: optional operating-system exit code;
- `stderr`: exact opaque bytes, including non-UTF-8 data.

Exit evidence is diagnostic transport data. It is not parsed into Protocol fields, copied into canonical payloads, or mapped to SOL evaluation/lifecycle terminology.

## Executable error matrix

| Stimulus | Primary caller-visible category | Secondary process evidence | Rule |
|---|---|---|---|
| malformed JSON response | `ResponseEnvelope` / `InvalidJson` | exit status and raw stderr after shutdown | never ProtocolFailure |
| valid JSON with invalid JSON-RPC response envelope | `ResponseEnvelope` / `InvalidEnvelope` | exit status and raw stderr after shutdown | never Protocol success |
| malformed request received by the worker | JSON-RPC `-32700` | worker stays transport-only | `error`, never `result` |
| invalid request envelope received by the worker | JSON-RPC `-32600` | worker stays transport-only | recognizable ID may be correlated |
| unknown method received by the worker | JSON-RPC `-32601` | worker stays transport-only | no unapproved dispatch |
| child stdin has no reader | `StdinBrokenPipe` | abnormal exit code and raw stderr after shutdown | session faults; no resend |
| stdout EOF before response | `StdoutEof` | clean or abnormal exit remains separate | EOF does not invent an operation result |
| child panic/crash | `StdoutEof` for the pending call | nonzero/optional exit code and raw stderr | diagnostic evidence stays opaque |
| explicit abnormal exit | `StdoutEof` for the pending call | exact nonzero exit code and raw stderr | exit code has no Protocol meaning |
| human text on stdout | `ResponseEnvelope` / `InvalidJson` | ordinary process evidence | stdout is protocol-only |
| invalid UTF-8 on stdout | `Framing` / `InvalidUtf8` | ordinary process evidence | invalid bytes are not coerced |
| arbitrary stderr bytes | no operation result by themselves | exact raw bytes in `AdapterProcessExit` | stderr has no semantic authority |
| valid operation returns ProtocolFailure | `AdapterOperationResult::ProtocolFailure` | session remains ready | remains JSON-RPC result payload |

`AdapterSessionErrorKind` is a stable category surface. Variant detail strings and raw stderr are debugging evidence, not canonical semantic identity.

## Ordering and ambiguity

The pending operation error is returned first. Process exit evidence is collected separately during shutdown. A response timeout, broken pipe, EOF, crash, or malformed response says only that a valid correlated response was not obtained; it does not prove whether `execute_plan` produced side effects.

The client never submits another operation on a faulted session and never resends the failed request. Phase 4 #79 owns reconnect policy and ambiguous-execution safety; Phase 3 introduces no replay authority, retry flag, idempotency inference, or deduplication token.

## Rejected counterexamples

```text
transport/process error -> ProtocolFailure
transport/process error -> PASS/FAIL/BLOCKED/INDETERMINATE
response loss -> automatic retry
stderr text -> Protocol or SOL semantics
child exit code -> Adapter Protocol outcome
malformed stdout -> best-effort Protocol payload
EOF -> proof that execute_plan had no side effects
timeout -> permission to allocate and send a replacement request
```

## Diagnostic privacy and backend boundaries

The transport preserves stderr bytes so callers can retain debugging evidence, but does not inspect backend-native terms or elevate them into Protocol or SOL identity. Higher layers may redact or store diagnostics according to deployment policy; they must not use text matching to classify a canonical outcome.

The deterministic fault peer is a solver-independent test executable. It emits controlled malformed responses, EOF, panic, abnormal exit, broken-pipe setup, raw stderr bytes, and one valid ProtocolFailure. It is test evidence only and introduces no backend runtime dependency.

## Phase handoff

Phase 4 #79 must consume this error/evidence boundary without silently replaying non-idempotent `execute_plan`. Reconnect may create a new transport session, but it cannot reinterpret the prior operation or discard ambiguity evidence.
