# M0.9 Adapter Runtime 0.2 Integration — Exit Candidate

## Scope

M0.9 integrates the already-published Public Contract 0.2 / Adapter Protocol 0.2 realization boundary into the accepted solver-neutral Adapter Runtime. It does not redefine Public Contract or Adapter Protocol semantics and does not add backend-specific mapping or solver dependencies.

## Accepted runtime architecture

```text
Public Contract 0.1 + Adapter Protocol 0.1
        -> existing 0.1 runtime path

Public Contract 0.2 + Adapter Protocol 0.2 + RealizationSpec
        -> explicit RuntimeContractProfile
        -> live describe_adapter compatibility evidence
        -> profile-aware target/capability projection and selection
        -> typed validate_plan_v02 / execute_plan_v02
        -> external adapter process
```

`RuntimeContractProfile`, `BackendTarget`, `AdapterRegistration`, and `AdapterInstance` remain distinct concepts. Runtime routes canonical payloads but does not interpret or invent realization semantics.

## Exit evidence implemented by this candidate

A standalone Cargo project at `examples/external-runtime-v02/` is outside the root workspace and consumes the public runtime API. CI supplies external adapter commands and the canonical thermal Protocol 0.2 fixture, then proves:

1. explicit local registration;
2. external process launch and `describe_adapter` bootstrap;
3. exact Protocol 0.2 / Public Contract 0.2 live compatibility;
4. solver-neutral target/capability projection;
5. deterministic profile-aware adapter selection;
6. full `target + plan + realization_spec` preservation through 0.2 validation;
7. full `target + plan + realization_spec` preservation through authoritative 0.2 execution;
8. successful external-process shutdown;
9. deterministic evidence output across repeated runs.

The external negative matrix also proves:

- a live 0.1 adapter is not eligible for an explicit 0.2 selection request;
- two eligible 0.2 adapters remain `Ambiguous` rather than being chosen arbitrarily;
- adapter bootstrap/process failure remains a runtime/transport failure;
- execute response loss retains `TransportMustNotReplayExecution` and does not authorize automatic replay.

Earlier M0.9 phases additionally establish unsupported/mixed runtime-profile rejection, live incompatible/unknown compatibility behavior, 0.1 regression preservation, and request-relative Protocol 0.2 execute-response validation.

## Boundary verdict required

Passing this candidate establishes SOL runtime/protocol interoperability only. It does **not** establish solver-native physical/numerical correctness, MOOSE/COMSOL/Ansys mapping correctness, or backend V&V.

The exact candidate head and CI run are recorded in the Phase 4 PR/issue because a commit cannot durably self-reference its own final SHA. M0.9 closure still requires Validator approval of the exact green candidate, explicit final-merge approval, post-merge `main` verification, and parent completion synchronization.
