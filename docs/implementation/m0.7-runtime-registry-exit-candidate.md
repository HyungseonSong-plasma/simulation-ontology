## 1. Milestone purpose

M0.7 establishes a solver-neutral Core runtime around external adapter processes without promoting runtime state, solver-native objects, or local invocation metadata into canonical SOL semantics.

The accepted architecture remains:

```text
BackendTarget
  = canonical solver-independent target semantics

AdapterRegistration
  = Core-local locator/invocation configuration

AdapterInstance
  = live operational process/session state

BackendTarget != AdapterRegistration != AdapterInstance
```

Adapters remain external processes. Core does not import MOOSE, COMSOL, Ansys, or any other solver runtime solely to support adapter execution.

## 4. Adversarial/runtime coverage

M0.7 evidence is cumulative rather than duplicating all earlier tests in the final Phase.

The milestone covers:

- disabled registration does not launch;
- missing executable remains typed process/spawn evidence;
- mandatory bootstrap before typed use;
- malformed transport/process behavior remains separate from logical Protocol failure;
- missing compatibility evidence remains `Unknown`, not compatible;
- incompatible adapters are not eligible;
- wrong target or missing capabilities are not eligible;
- multiple compatible candidates remain explicit `Ambiguous` results;
- reconnect creates a fresh process/session identity;
- adapter package version never establishes compatibility;
- static registration metadata cannot override live description evidence;
- lost `execute_plan` response preserves `MayHaveOccurred` side-effect evidence and `TransportMustNotReplayExecution`;
- backend-native object/API identity never participates in canonical model or selection semantics;
- no solver-specific runtime dependency is required by Core.

Existing M0.6 external conformance tests, M0.5 transport/parity tests, and M0.8 Public Contract / Adapter Protocol schema/conformance tests remain active CI gates.

## 5. M0.8 coexistence and version boundary

M0.8 independently published Public Contract 0.2 / Adapter Protocol 0.2 with the `RealizationSpec` boundary.

M0.7 was accepted as a runtime/registry milestone around the published 0.1 process/session path. Therefore M0.7 does **not** infer runtime 0.2 execution support merely because 0.2 DTOs/schemas exist in the repository.

Current live discovery deliberately evaluates the accepted M0.7 runtime support profile (`CompatibilitySupport::current()`, the 0.1 pair). A future runtime extension may add explicit 0.2 transport/operation dispatch only with corresponding implementation and compatibility evidence.

This preserves both rules:

```text
0.1 runtime/session assumptions are not silently reinterpreted by M0.8
0.2 contract publication is not silently advertised as implemented runtime support
```

## 6. Semantic and product boundaries

Runtime concepts remain outside canonical ontology meaning:

- registration IDs;
- instance IDs;
- PIDs;
- program paths and arguments;
- working directories;
- JSON-RPC/request/session identifiers;
- process stderr/exit status.

They may be operational evidence but never canonical simulation identity.

Phase 4 projection is an internal solver-neutral precursor for future CLI/SDK/GUI use. M0.7 does not stabilize:

- a plugin marketplace;
- package/signing/update contracts;
- auto-discovery;
- stable GUI UX;
- stable TypeScript/Python SDK ABI;
- solver-specific configuration editors.

## 7. Conformance and physical correctness

Runtime interoperability/conformance evidence does not establish backend physical or numerical correctness.

M0.7 proves that Core can locate, launch, inspect, select, and dispatch to an adapter according to the published SOL contract/runtime boundaries. It does not prove that a real MOOSE/COMSOL/Ansys realization is physically correct, numerically converged, or validated against a benchmark.

Those remain adapter/backend V&V responsibilities.
