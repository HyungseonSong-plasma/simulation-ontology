# M0.7 Phase 0 — Runtime Boundary & Registration Model

**Status:** Implementation candidate  
**Date:** 2026-08-22  
**Parent:** #111  
**Phase:** #112  
**Governing ADR:** `docs/adr/ADR-003-adapter-runtime-registration-boundary.md`

## Purpose

Phase 0 introduces the smallest executable Core-local runtime model needed to keep canonical backend-target semantics separate from adapter registration and live process/session state.

The implementation intentionally does not start a process, persist a registry, evaluate compatibility, select an adapter, or change Adapter Protocol/Public Contract semantics. Those concerns belong to later M0.7 phases.

## Implemented boundary

A new workspace crate owns runtime-local data:

```text
crates/sol-adapter-runtime
```

It defines:

```text
AdapterRegistrationId
AdapterCommand
AdapterRegistration
AdapterInstanceId
AdapterInstance
```

The existing canonical target concept remains in `sol-target-resolver`:

```text
BackendTarget
```

No duplicate `BackendTarget` is introduced in the runtime crate.

### Registration

`AdapterRegistration` contains only:

- a local registration identifier;
- executable/program path;
- command arguments;
- optional working directory.

It does **not** contain or establish:

- backend target truth;
- capability truth;
- supported Adapter Protocol versions;
- supported Public Contract versions;
- adapter implementation/package compatibility.

Those facts must come from live Adapter Protocol bootstrap evidence in later phases.

### Instance

`AdapterInstance` contains operational bookkeeping only:

- local instance identifier;
- originating local registration identifier;
- process identifier.

These values are not canonical SOL identity and are not serialized as Public Contract DTOs.

The runtime crate deliberately has no Serde/Public Contract dependency and no solver-native runtime dependency.

## Executable architecture evidence

The architecture counterexample suite now covers the M0.7 runtime boundary.

Golden behavior requires all of the following to remain false:

```text
BackendTarget == AdapterRegistration
AdapterRegistration == AdapterInstance
registration declares Protocol compatibility truth
registration declares Public Contract compatibility truth
registration declares capability truth
runtime identity affects canonical identity
backend-native identity affects canonical identity
```

Counterexamples explicitly reject:

- registration/target conflation;
- registration/instance conflation;
- static registration treated as interoperability authority;
- PID/session/runtime/backend-native identity treated as canonical semantic identity.

The architecture test also scans the runtime crate's normal dependencies and rejects backend-native solver dependency leakage.

## Phase boundary

Phase 0 does not define:

- registry add/remove/list/enable-disable behavior — Phase 1;
- subprocess launch/bootstrap/close/reconnect — Phase 2;
- dual compatibility/capability discovery — Phase 3;
- target/capability-based adapter selection — Phase 4;
- full external runtime integration / milestone exit — Phase 5.

This keeps Phase 0 limited to the accepted runtime type/boundary foundation.

## Compatibility

No Adapter Protocol 0.1 or Public Contract 0.1 DTO/schema/semantic meaning is changed by this phase.

No solver-specific runtime dependency is added to Core.

## Exit evidence

Phase 0 is complete only after the exact implementation PR head passes the repository-required formatting, workspace build/tests, standalone external-project conformance workflow, Clippy, architecture counterexamples, Public Contract schema validation, and Adapter Protocol schema validation, followed by merge and `main` verification.
