# M0.7 Phase 3 — Live Compatibility & Capability Discovery

Status: implementation candidate for #115

## Purpose

Phase 3 turns the already-mandatory `describe_adapter` bootstrap result into solver-neutral runtime evidence. It does not add registration metadata, redefine Adapter Protocol compatibility, or create SOL lifecycle semantics.

## Evidence flow

```text
explicit local AdapterRegistration
        |
        | locate / launch only
        v
external adapter process
        |
        | mandatory describe_adapter
        v
AdapterDescription
  bootstrap compatibility declarations
  target declarations
  capability declarations
        |
        v
LiveAdapterEvidence
  CompatibilityAssessment
  normalized target/capability evidence
```

The registration remains a local locator/configuration record. It has no fields that can declare or override Protocol compatibility, Public Contract compatibility, target support, or capabilities.

## Compatibility authority

Phase 3 reuses the published Adapter Protocol compatibility algebra:

```text
Adapter Protocol axis    Compatible | Incompatible | Unknown
Public Contract axis     Compatible | Incompatible | Unknown

any incompatible axis    -> overall Incompatible
both compatible          -> overall Compatible
otherwise                -> overall Unknown
```

Adapter implementation/package version is observed metadata only. It never establishes interoperability.

Missing support information is `Unknown`, not compatible. Malformed bootstrap/description evidence is rejected by the existing Adapter Protocol parser/session boundary rather than silently accepted.

## Runtime version scope

M0.7 was accepted against the published 0.1 runtime/transport path. M0.8 later published an additive Public Contract 0.2 / Adapter Protocol 0.2 realization contract.

Phase 3 therefore evaluates the existing M0.7 live runtime against `CompatibilitySupport::current()` (the 0.1 pair). The existence of 0.2 schemas/DTOs does not itself prove that the current runtime/session path supports 0.2 execution.

A later explicit runtime integration may add 0.2 support only with corresponding transport/operation evidence; it must not be inferred implicitly here.

## Target and capability evidence

Targets and capabilities are copied from the normalized live `AdapterDescription`. They remain Adapter Protocol declarations associated with one operational `AdapterInstanceId`.

They are not:

- canonical ontology entities;
- backend-native solver object identities;
- static registration claims;
- SOL lifecycle results;
- proof of backend physical/numerical correctness.

## Lifecycle separation

`CompatibilityOutcome::{Compatible, Incompatible, Unknown}` is runtime interoperability evidence only. It MUST NOT be translated directly into SOL `PASS`, `FAIL`, `BLOCKED`, or `INDETERMINATE` states.

## Executable evidence

Phase 3 tests cover:

- a dual-compatible description exposing normalized target/capability declarations;
- package-version equality not overriding incompatible Protocol evidence;
- missing compatibility support remaining `Unknown`;
- explicit 0.2 support checks not being inferred from the current 0.1 runtime profile;
- a real external `sol-mock-adapter-stdio` process producing live evidence only after mandatory bootstrap.

Existing Adapter Protocol positive/adversarial compatibility fixtures remain the normative compatibility input and are reused rather than duplicated in the runtime layer.

## Out of scope

- new Adapter Protocol fields or meanings;
- Protocol/Public Contract 0.2 transport execution integration;
- dynamic capability event streams;
- solver-native capability semantics;
- adapter selection policy (Phase 4);
- GUI/SDK stabilization;
- backend physical/numerical V&V.
