# M0.6 Conformance Runner Boundary and Result Model

**Status:** Phase 0 implementation record  
**Date:** 2026-08-22  
**Milestone:** M0.6 Adapter Conformance Tooling  
**Parent tracker:** #81  
**Phase:** #82  
**Dependency:** completed M0.5 local process transport

## Purpose

This phase defines the reusable Core-side model for recording external-adapter
conformance evidence. It establishes what the runner may and may not conclude before
M0.6 adds external invocation, fixture execution, authoring scaffolding, or a productized
command surface.

Conformance means that observed adapter behavior agrees with versioned, published SOL
Adapter Protocol and Public Contract expectations for the cases actually executed. It is
an interoperability claim bounded by those expectations and observations.

It is not a claim that a solver, discretization, material model, numerical method, or
backend-native result is physically correct.

## Accepted conformance scope

The model can classify a case along every accepted Phase 0 dimension:

| Dimension | Meaning |
| --- | --- |
| Compatibility | Adapter Protocol or Public Contract version negotiation |
| Schema | Published Adapter Protocol or Public Contract shape constraints |
| Fixture | Versioned published positive or counterexample material |
| Operation semantics | `describe_adapter`, `validate_plan`, or `execute_plan` behavior |
| Scheduling | Dependency-safe ordering and coverage expectations |
| Failure and replay | Protocol failures, operation-specific retry safety, and ambiguity |
| Provenance | Opaque evidence without backend identity leakage |

`ProtocolOperation` is reused from `sol-adapter-protocol`; the conformance model does not
invent a second operation vocabulary. Adapter Protocol 0.1 and Public Contract 0.1 remain
unchanged.

## Case result algebra

Each case has one of three conformance-specific results:

1. `Conformant(evidence)` — the published expectation was observed.
2. `NonConformant(violation)` — the published expectation was contradicted.
3. `HarnessFailure(kind, detail)` — the runner could not establish the case because its
   fixture loading, invocation, transport exchange, decoding, or own invariant failed.

These are conformance-runner terms only. They do not reuse or project into SOL lifecycle
or evaluation states.

The aggregate determination is deterministic:

- any observed violation yields `NonConformant`;
- otherwise any harness failure yields `NotEstablished`;
- otherwise all cases establish `Conformant`.

An empty report is rejected, case identifiers are non-blank and unique, and report cases
are sorted by identifier. This makes the in-memory report deterministic without defining
a serialized report contract in Phase 0.

## Failure boundary

A `ProtocolFailure` is a normal logical Adapter Protocol result. A conformance case may
expect a particular `ProtocolFailure`, so receiving one is not inherently a violation.
Whether it conforms depends on the case expectation.

By contrast, a runner that cannot start an adapter, exchange a frame, load a fixture, or
decode an observation has a harness failure. The runner has insufficient evidence for
that case and must not accuse the adapter of non-conformance merely because the harness
failed.

Transport and process errors remain M0.5 transport evidence. They are not rewritten into
Adapter Protocol payload meaning.

## Backend correctness exclusion

Every `ConformanceReport` exposes backend validation scope as
`NotAssessedByConformance`. External adapter projects remain responsible for any
solver-native physical, numerical, mesh, material, convergence, or vendor-runtime
validation appropriate to their domain.

Passing the SOL conformance suite therefore supports an interoperability statement only.
It cannot be used as evidence that the backend's scientific result is correct.

## Phase 0 public-interface status

Phase 0 publishes only an internal Rust boundary model for later M0.6 implementation. It
does not stabilize:

- a conformance binary name;
- command or option spelling;
- exit codes;
- stdout or stderr formatting;
- a JSON result schema;
- fixture discovery paths; or
- package/distribution names.

Any normative CLI or output contract requires explicit public-interface review before it
is stabilized. Later phases may implement a provisional invocation path without treating
its exact spelling or rendering as a compatibility promise.

## Rejected counterexamples

The following implications are explicitly invalid:

```text
conformance success -> solver-native physical correctness
ProtocolFailure -> conformance violation
harness failure -> adapter non-conformance
runner result -> SOL lifecycle state
exact CLI spelling in Phase 0 -> stable public interface
transport failure -> ProtocolFailure
```

These are executable documentation constraints: the Phase 0 tests require this record to
retain them.

## Phase 1 handoff

Phase 1 may build an external-adapter invocation harness on the completed M0.5 process
transport. It should translate invocation and transport observations into
`HarnessFailure` without changing Protocol 0.1 semantics, and should feed case results
into this deterministic report model.

Phase 1 must keep exact CLI spelling and serialized output provisional unless a separate
public-interface decision explicitly accepts them.
