# M0.6 External Adapter Invocation Harness

**Status:** Phase 1 implementation record  
**Date:** 2026-08-22  
**Milestone:** M0.6 Adapter Conformance Tooling  
**Parent tracker:** #81  
**Phase:** #83  
**Depends on:** completed Phase 0 #82 and M0.5 process transport

## Purpose

Phase 1 adds a reusable harness for launching an arbitrary external adapter command and
observing published Adapter Protocol 0.1 behavior through the completed local
JSON-RPC/stdin-stdout transport.

The production harness depends on the Phase 0 conformance model, Adapter Protocol, and
adapter transport only. It does not depend on MockAdapter, a real solver, a vendor SDK,
or an adapter package. MockAdapter is a development-only external command used to prove
the boundary.

## Crate boundary

The sol-adapter-conformance crate remains a pure result-model crate with no process or
transport dependency. The sol-adapter-conformance-harness crate composes that model with
sol-adapter-transport.

This split keeps fixture/report semantics usable without process ownership while giving
later runner phases a typed external invocation path.

The harness accepts a program plus opaque arguments. M0.5 owns child-process creation,
stdio framing, JSON-RPC request correlation, timeout behavior, typed Protocol payload
decoding, and shutdown. The harness does not invoke language-specific adapter libraries.

## Launch and compatibility

Launch always begins with the M0.5 describe_adapter bootstrap exchange. A successful
description is assessed against Core's current compatibility support on both independent
axes:

- Adapter Protocol version support; and
- Public Contract version support.

The complete CompatibilityAssessment is retained on the ready harness session.
Compatible, Incompatible, and Unknown remain distinct. Merely starting a process or
receiving a description does not imply that compatibility was established.

A logical ProtocolFailure returned during bootstrap is an
ExternalAdapterLaunch::ProtocolFailure observation. It is not a harness invocation
error.

## Operation channels

Ready sessions carry typed ValidatePlanRequest and ExecutePlanRequest values through the
M0.5 transport. Each call has two independent channels:

1. AdapterProtocolObservation::Success or
   AdapterProtocolObservation::ProtocolFailure for logical Protocol results; and
2. HarnessInvocationError for invocation, timeout, framing, correlation, JSON-RPC,
   payload-decoding, or harness-invariant failures.

This lets later fixture cases decide whether a particular Protocol failure is the
expected conformant result. The harness never treats the mere presence of a
ProtocolFailure as non-conformance.

## Deterministic harness evidence

Every harness error records:

- the stable invocation stage (process start, bootstrap, compatibility assessment,
  validate_plan, execute_plan, or shutdown);
- the typed M0.5 AdapterSessionError or compatibility/invariant evidence;
- the stable AdapterSessionErrorKind when transport/session evidence exists; and
- a Phase 0 HarnessFailure category and non-blank detail suitable for a conformance case
  report.

The mapping is:

| Source | Conformance harness category |
| --- | --- |
| process spawn | AdapterInvocation |
| Protocol payload decoding | ResultDecoding |
| session/request/reader invariants | RunnerInvariant |
| timeout, stdio, framing, envelope, correlation, JSON-RPC, shutdown | TransportExchange |

Normal and abnormal shutdown evidence retains success, optional exit code, and raw stderr
bytes. stderr remains opaque evidence; it is not parsed into Protocol, lifecycle, or
semantic identity.

## Identity and dependency boundary

The harness exposes command program/arguments and typed observations but does not expose
or consume an operating-system process ID. Process identity, JSON-RPC request identity,
and adapter package identity cannot become SOL semantic identity.

An external adapter project owns its language runtime, solver libraries, vendor SDKs,
installation, and backend-native validation. None of those dependencies enter the Core
workspace through this harness.

## Public-interface status

The Rust types in this phase are an implementation surface for subsequent M0.6 work.
Phase 1 does not stabilize a standalone conformance executable name, shell syntax,
environment contract, exit-code policy, fixture search path, or serialized report
format. Those remain subject to explicit public-interface review.

## Rejected counterexamples

The following implications are invalid:

    bootstrap ProtocolFailure -> harness failure
    process ID -> SOL semantic identity
    transport timeout -> adapter non-conformance
    harness launch success -> compatibility established
    adapter package -> Core runtime dependency
    provisional command spelling -> stable public interface

The external MockAdapter integration test requires this record to retain those rejected
counterexamples.

## Phase 2 handoff

Phase 2 may load versioned Adapter Protocol and Public Contract fixtures, invoke them
through this harness, compare typed/canonical observations with fixture expectations, and
produce Phase 0 case records.

Fixture loading failures must map to HarnessFailureKind::FixtureLoad; Protocol logical
failures and transport failures must remain on their distinct channels. Exact command
spelling and serialized report output remain provisional until explicitly reviewed.
