# M0.5 stdio Process Lifecycle and Adapter Session

**Status:** Phase 2 executable process profile
**Date:** 2026-08-22
**Milestone:** M0.5 — JSON-RPC / stdio Transport
**Parent tracker:** #74
**Phase:** #77
**Depends on:** Phase 1 #76 / PR #97

## Purpose

This profile connects the Phase 1 JSON-RPC/framing layer to a local adapter child process while keeping process and session state outside Adapter Protocol and SOL semantics.

The implementation consists of a solver-independent generic client session in `sol-adapter-transport` and a `sol-mock-adapter-stdio` reference worker. The transport crate does not depend on MockAdapter; the reference worker depends inward on the transport and published Protocol crates.

## Process ownership

The client owns one child process and its three standard streams:

| Stream | Ownership and rule |
|---|---|
| stdin | Client-owned request channel; canonical LF JSON-RPC frames only |
| stdout | Child-owned response channel; canonical LF JSON-RPC frames only |
| stderr | Diagnostic byte stream drained concurrently and returned as shutdown evidence |

The stdout reader and stderr drainer run independently so diagnostic output cannot block protocol responses. The worker never writes logs or human text to stdout.

No operating-system process ID is exposed by the session API. Program path, arguments, pipe handles, thread handles, and exit status are transport implementation data only.

## Startup and readiness

Startup is a deterministic state transition:

```text
Starting
  -> spawn child with piped stdin/stdout/stderr
  -> start stdout frame reader and stderr drainer
  -> allocate request ID 1
  -> send describe_adapter
  -> correlate and validate the response
  -> Ready
```

A successful process spawn is not readiness. The session becomes `Ready` only after `describe_adapter` returns a canonical `AdapterDescription`. A bootstrap `ProtocolFailure` remains a `ProtocolFailure`; spawn, framing, timeout, JSON-RPC, correlation, and payload errors remain transport/session errors.

If bootstrap fails, the client closes stdin, terminates and waits for the child, joins both reader threads, and returns the original startup error. No partially ready session escapes.

## One-session request/response lifecycle

The Phase 2 client permits one outstanding request at a time through mutable session access:

1. require `Ready`;
2. canonicalize the typed Protocol request;
3. allocate a fresh monotonic transport request ID;
4. write and flush one Phase 1 frame;
5. wait for one stdout frame;
6. decode the JSON-RPC response and correlate the exact ID;
7. return typed Protocol success or typed `ProtocolFailure`.

The ID is discarded at the transport boundary. It is not passed to MockAdapter and is not copied into Protocol request/response payloads.

The reference worker decodes the envelope, parses the nested typed request, invokes the unchanged in-process MockAdapter operation, and wraps the canonical typed result. A known method with an object that fails Protocol parsing returns published invalid-request `ProtocolFailure` under the JSON-RPC result channel.

## Timeout and no-retry rule

Each exchange has a bounded response wait, five seconds by default. Timeout stops the current call with a transport/session error. It does not resend the request, allocate a replacement request, infer whether execution happened, or classify SOL lifecycle state.

Any exchange-level framing, read, timeout, envelope, correlation, or JSON-RPC error moves a ready session to transport-only `Faulted` state. A faulted session cannot submit another operation; the caller must shut it down or drop it. This prevents a stale response from being consumed by a later call and prevents accidental same-session replay.

Detailed timeout, EOF, broken-pipe, child-exit, and stderr evidence categories remain Phase 3. Reconnect and ambiguous execution decisions remain Phase 4.

## Shutdown

Explicit clean shutdown follows this order:

1. drop the client stdin handle, delivering EOF to the worker;
2. worker finishes any complete frames and exits normally;
3. client polls for exit up to the configured response timeout;
4. client waits for and records exit status;
5. client joins stdout and stderr reader threads;
6. client returns transport-only exit code/success/stderr evidence and enters `Stopped`.

If the process does not exit after stdin closes, the client kills and reaps it and reports a shutdown timeout. Dropping a live session performs best-effort immediate termination and reaping; it never replays an operation.

## Executable reference path

The integration test launches the Cargo-built `sol-mock-adapter-stdio` binary, verifies bootstrap description equality with the in-process MockAdapter, sends the published accepted `validate_plan` fixture and thermal `execute_plan` fixture in one session, compares typed results with the in-process operations, then verifies clean exit code 0 and empty stderr.

This is Phase 2 lifecycle integration evidence. The complete positive/adversarial in-process/subprocess parity matrix remains Phase 5.

## Rejected counterexamples

```text
process state -> Adapter Protocol semantic state
process ID -> SOL semantic identity
startup success -> SOL lifecycle state
response timeout -> automatic retry
EOF -> no execute side effects
child exit code -> ProtocolFailure
stderr text -> canonical Protocol identity
session reconnect -> Phase 2 behavior
network transport -> Phase 2 scope
```
