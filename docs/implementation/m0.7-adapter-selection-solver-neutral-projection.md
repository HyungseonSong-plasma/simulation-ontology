# M0.7 Phase 4 — Adapter Selection & Solver-neutral Projection

Status: implementation candidate for #116

## Purpose

Phase 4 turns live Adapter Protocol evidence into a deterministic, solver-neutral runtime projection and selection result. It does not choose adapters by solver-specific code paths and does not stabilize a GUI/SDK plugin surface.

## Projection

```text
RunningAdapter
  local AdapterRegistrationId
  local AdapterInstanceId
        |
        +-> live describe_adapter
               |
               v
        LiveAdapterEvidence
               |
               v
        AdapterRuntimeProjection
          adapter implementation metadata
          dual-axis compatibility
          canonical BackendTarget projection
          declared capability set
```

Registration and instance IDs remain runtime-local. Adapter IDs/versions, target declarations, and capabilities come from the live Protocol description. No backend-native solver object/API identity participates.

## Eligibility

An adapter target is eligible only when all of the following hold:

1. the live compatibility outcome is `Compatible`;
2. the declared target exactly matches the canonical `BackendTarget` requested by Core/user intent;
3. every required `BackendCapability` is present in that live target declaration.

`Unknown` and `Incompatible` adapters are not eligible.

## Deterministic outcomes

Selection deliberately has three result shapes:

```text
0 eligible  -> NoCompatibleCandidate
1 eligible  -> Selected(candidate)
2+ eligible -> Ambiguous(sorted candidates)
```

Multiple compatible adapters are not resolved by hidden first-item/min-ID selection. The ambiguous candidate list is sorted deterministically by live adapter ID, then local registration ID, then local instance ID so callers can present an explicit choice without nondeterminism.

## Solver-neutral boundary

The generic selection algorithm depends only on:

- canonical `BackendTarget`;
- canonical required `BackendCapability` values;
- live Protocol compatibility evidence;
- live target/capability declarations;
- local registration/instance identities for operational disambiguation.

It contains no solver-specific MOOSE/COMSOL/Ansys branch and does not interpret backend-native object identities.

## Projection boundary

`AdapterRuntimeProjection` is suitable as an internal precursor for future CLI/SDK/GUI views, but M0.7 does not stabilize its exact serialization, UI labels, package format, or public SDK ABI.

## Tests

Phase 4 executable tests cover:

- zero eligible candidates from wrong target, missing capability, or incompatible evidence;
- exactly one eligible candidate;
- multiple eligible candidates reported as `Ambiguous` in deterministic order;
- `Unknown` compatibility excluded from eligibility.

## Out of scope

- stable GUI UX;
- plugin marketplace/package discovery;
- automatic installation/update;
- stable TypeScript/Python SDK contract;
- solver-specific configuration editors;
- backend-native semantic identity;
- physical/numerical V&V.
