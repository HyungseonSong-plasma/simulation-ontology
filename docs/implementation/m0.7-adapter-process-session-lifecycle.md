# M0.7 Phase 2 — Adapter Process & Session Lifecycle

**Status:** Implementation candidate  
**Date:** 2026-08-22  
**Parent:** #111  
**Phase:** #114  
**Depends on:** completed Phase 1 #113

## Purpose

Phase 2 composes the explicit local registration model with the accepted M0.5 JSON-RPC/stdin-stdout process transport. It does not introduce a second transport implementation or change Adapter Protocol 0.1 semantics.

## Runtime lifecycle

`sol-adapter-runtime` now exposes `RunningAdapter`.

Launch path:

```text
AdapterRegistryEntry (enabled)
  -> AdapterCommand
  -> AdapterProcessCommand
  -> AdapterProcessSession::spawn
  -> mandatory describe_adapter bootstrap
  -> Ready RunningAdapter
  -> AdapterInstance(local instance ID, registration ID, PID)
```

The runtime preserves registration arguments and optional working directory when constructing the transport command.

The only additive M0.5 transport changes are operational accessors/configuration needed by the runtime:

- `AdapterProcessCommand::current_dir(...)` and `working_directory()`;
- `AdapterProcessSession::process_id()`.

These values remain transport/runtime-local and do not enter Adapter Protocol or Public Contract payload semantics.

## Failure separation

Runtime operation calls preserve the M0.5 channel separation:

```text
Protocol logical outcome
  -> AdapterOperationResult::Success | ProtocolFailure

transport/process/session failure
  -> AdapterRuntimeError::Transport(AdapterSessionError)
```

The runtime does not map transport errors or Protocol failures to SOL lifecycle states.

Existing M0.5 error categories remain unchanged, including spawn, framing, EOF, timeout, broken pipe, response envelope, correlation, remote JSON-RPC, Protocol payload, bootstrap ProtocolFailure, shutdown, and reader-thread failures.

## Stop and reconnect

`RunningAdapter::shutdown` delegates to the accepted transport shutdown behavior: close stdin, wait for process exit, collect stderr, and return `AdapterProcessExit`.

`RunningAdapter::reconnect` is explicit and creates a new process/session:

1. require the same explicit registration identity;
2. shut down the current process;
3. require a new `AdapterInstanceId`;
4. launch the currently enabled registration again;
5. bootstrap again through `describe_adapter` before returning Ready.

No continuity of backend/session state is inferred from reconnect.

## Response-loss / replay invariant

The runtime reuses M0.5 `response_loss_recovery` directly. For `execute_plan`:

```text
replay = TransportMustNotReplayExecution
conservative_side_effects = MayHaveOccurred
```

No runtime retry loop is introduced around `execute_plan`.

## Executable evidence

Runtime tests cover:

- invocation argument and working-directory preservation;
- disabled registrations are not launched;
- a registered `sol-mock-adapter-stdio` external process launches and completes mandatory bootstrap;
- reconnect shuts down the old session and returns a newly bootstrapped session with a new local instance identity;
- execute response-loss policy remains no-transport-replay / possible-side-effect.

The external-process runtime test intentionally uses the existing M0.4/M0.5 MockAdapter stdio binary built by the workspace. It is evidence of generic runtime/process integration, not solver-native correctness.

The pre-existing M0.5 full transport/parity/error tests remain part of workspace CI and therefore continue to gate Phase 2.

## Compatibility

Phase 2 changes no Adapter Protocol 0.1 operation or payload, no Public Contract 0.1 schema/semantic meaning, and adds no solver-specific dependency to Core.

`AdapterDescription` is exposed as live bootstrap evidence only. Compatibility/capability interpretation remains Phase 3.

## Exit evidence

Phase 2 completes only after exact-head CI passes all repository gates, the implementation PR merges, and `main` is verified identical.
