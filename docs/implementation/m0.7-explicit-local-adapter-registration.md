# M0.7 Phase 1 — Explicit Local Adapter Registration

**Status:** Implementation candidate  
**Date:** 2026-08-22  
**Parent:** #111  
**Phase:** #113  
**Depends on:** completed Phase 0 #112

## Purpose

Phase 1 adds deterministic in-memory registration behavior for explicitly supplied external adapter commands while preserving ADR-003's runtime/semantic boundary.

## Implemented registry API

`sol-adapter-runtime` now exposes an `AdapterRegistry` that supports:

- explicit `register`;
- `get` by local registration ID;
- deterministic `entries` iteration;
- `set_enabled` for enable/disable state;
- `remove`;
- `len` / `is_empty`.

Registrations are enabled by default. A duplicate local registration ID is rejected with `AdapterRegistryError::DuplicateRegistration` rather than silently replacing the existing command. Enable/disable of an unknown ID returns `AdapterRegistryError::UnknownRegistration`.

The registry uses ordered local registration IDs, so equivalent registry content produces deterministic listing order independent of insertion order.

## Boundary preserved

Registration remains local runtime configuration. It contains only the Phase 0 invocation data:

```text
local registration ID
program path
arguments
optional working directory
```

The registry does not record trusted:

```text
BackendTarget
Adapter Protocol compatibility
Public Contract compatibility
backend capabilities
```

Those are live-bootstrap concerns for later M0.7 phases.

Enable/disable is also local runtime eligibility state; it does not establish interoperability or semantic validity.

## Intentionally absent

Phase 1 introduces no:

- directory scanning or automatic discovery;
- adapter package/manifest standard;
- persistence file format;
- remote registry;
- marketplace;
- download/install behavior;
- signing/trust distribution;
- auto-update;
- GUI product surface;
- solver-specific runtime dependency.

The exact persistence/config-file and CLI surface therefore remain Experimental/uncommitted as required by the accepted plan.

## Validation

Unit tests cover:

- explicit add/read/disable/enable/remove lifecycle;
- duplicate-ID rejection without replacement;
- deterministic listing by registration ID;
- explicit unknown-registration enable/disable error.

Phase 0 architecture counterexamples remain in force, including no static interoperability truth and no backend-native dependency/identity leakage.

## Exit evidence

Phase 1 completes only after the exact implementation PR head passes all repository-required CI gates, merges, and is verified identical to `main`.
