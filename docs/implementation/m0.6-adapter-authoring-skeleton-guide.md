# M0.6 Phase 4 — Adapter Authoring Skeleton & Guide

Issue: #86

## Scope

Phase 4 provides compile-checked, solver-independent reference scaffolding for an external Adapter Protocol 0.1 implementation and an authoring guide. It does not stabilize a new Protocol surface, conformance CLI, report serialization, fixture-distribution mechanism, SDK, or real solver adapter.

## Reference structure

`examples/adapter-authoring/rust-stdio/` contains three deliberately separate responsibilities:

1. `src/lib.rs` — Protocol-facing adapter logic using published Adapter Protocol/Public Contract DTOs;
2. `src/main.rs` — M0.5 JSON-RPC/stdin-stdout transport mapping;
3. `tests/conformance.rs` — subprocess conformance evidence through `PublishedPositiveFixtureSuite`.

The example is a workspace member only so repository CI compiles and tests it. The architecture remains external-command based: the conformance runner does not link the adapter implementation to observe behavior.

## Authoring boundary

The sample target/capability/action values match the published `mock` thermal fixture baseline. They are fixture-compatible example semantics, not a target vocabulary that real adapters must adopt.

A real adapter replaces the sample backend mapping while preserving:

- dual Adapter Protocol/Public Contract compatibility evidence;
- published request/response DTO meaning;
- advisory, side-effect-free `validate_plan`;
- authoritative current-state `execute_plan`;
- dependency-safe scheduling and aggregate-effect invariants;
- ProtocolFailure/transport/lifecycle separation;
- conservative execute side-effect evidence;
- canonical semantic identity separated from opaque backend provenance.

## Rejected interpretations

The Phase 4 material explicitly rejects:

```text
reference skeleton -> new normative Protocol API
workspace membership -> Core links a solver runtime
adapter version -> Protocol/Public Contract compatibility
accepted preflight -> durable execution authority
lost execute response -> automatic replay
opaque backend reference -> canonical semantic identity
Protocol conformance -> backend physical or numerical correctness
sample mock target -> required real-adapter target naming
cargo test command -> stabilized conformance CLI/output contract
```

## Validation intent

The reference integration test must launch the skeleton executable through the external adapter harness and establish the published positive fixture baseline. The skeleton manifest must contain no MockAdapter or solver/vendor dependency. The guide must preserve the non-normative, provenance, replay, public-interface, and physical-correctness boundaries.

Full Rust Core CI remains the Phase gate: formatting, workspace build/tests, Clippy, architecture counterexamples, and both published JSON Schema gates.

## Deferred to Phase 5

Phase 5 owns the external-project workflow and milestone exit evidence, including running a repository-external-style adapter command against reusable conformance material and the final Validator audit. Exact conformance CLI spelling, exit codes, serialized report schema, and fixture distribution remain provisional until explicitly decided.
