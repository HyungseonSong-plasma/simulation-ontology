# M0.3 Phase 0 — Adapter Protocol Responsibility Inventory

**Date:** 2026-08-21  
**Issue:** #39  
**Normative architecture:** `docs/adr/ADR-002-adapter-protocol-boundary.md`

## Purpose

This inventory maps the product-roadmap adapter responsibilities onto the accepted Core/Public Contract/Adapter Protocol boundary before any Protocol 0.1 DTO or wire schema is implemented.

## Classification vocabulary

- **Core-local** — semantic/runtime responsibility that does not automatically become a remote operation.
- **Adapter-internal** — backend implementation responsibility hidden behind the protocol boundary.
- **Shared Public Contract payload** — canonical solver-independent semantic object already owned by Public Contract 0.1 and reused by the protocol.
- **Provenance/evidence metadata** — traceability information that may cross the boundary but must not define semantic identity/equality.
- **Public protocol operation** — an interoperability action that must be represented by Adapter Protocol 0.1.
- **Deferred transport** — JSON-RPC/process concerns owned by M0.5, not M0.3.

## Responsibility inventory

| Roadmap concern | Classification | Protocol consequence |
|---|---|---|
| Adapter identity and adapter implementation version | Public protocol metadata | Returned by adapter description/bootstrap; package version does not imply compatibility. |
| Supported Adapter Protocol range | Public protocol metadata | Required for Protocol compatibility assessment. |
| Supported Public Contract versions/range | Public protocol metadata | Required independently from Protocol compatibility. |
| Capability/target declaration and evidence | Public protocol metadata | Adapter declares; Core interprets for target resolution. |
| BackendTarget selection/resolution | Core-local | Must not become a standalone adapter selection RPC merely because Core performs it. |
| Canonical MappingPlan | Shared Public Contract payload | Reused directly; protocol must not define a duplicate plan shape. |
| MappingPlan DAG/dependency validation | Core-local semantic ownership | Adapter may preflight backend acceptance but does not redefine plan graph semantics. |
| Canonical deterministic plan ordering | Core-local representation rule | Preserved for canonical payloads; does not force physical execution order. |
| Backend physical scheduling | Adapter-internal | May reorder independent actions or parallelize while preserving dependencies/reporting. |
| Plan preflight/acceptance | Public protocol operation | `validate_plan` candidate; advisory only. |
| Plan execution | Public protocol operation | `execute_plan` candidate; authoritative for execution-time checks. |
| Backend realization | Adapter-internal | Solver/vendor APIs and native objects remain hidden. |
| Backend realization normalization | Adapter-internal | Produces canonical Public Contract realization/effect output. |
| Canonical realization/effect data | Shared Public Contract payload | Crosses boundary as canonical outcome/reporting, not vendor structures. |
| RealizationEffect comparison | Core-local | Core compares semantic intent to canonical realization evidence. |
| Evaluation lifecycle classification | Core-local | Protocol errors are never lifecycle states. |
| Backend job/artifact handle | Provenance/evidence metadata | May cross opaquely; Core semantics/equality must not depend on it. |
| Solver-native object/type/vendor API structure | Adapter-internal only | Forbidden from canonical semantic payloads/identity. |
| Adapter description/bootstrap | Public protocol operation | `describe_adapter` candidate; provides version-safe compatibility discovery. |
| JSON-RPC request IDs/envelopes | Deferred transport | M0.5 only. |
| stdio framing/process startup/shutdown | Deferred transport | M0.5 only. |
| retry/reconnect/backoff/replay | Deferred transport | M0.5 only; cannot assume execute idempotency. |
| General dynamic capability event stream | Deferred semantic model | Not part of Protocol 0.1 absent new Manager-approved evidence. |

## Candidate operation surface

The minimal Phase 0 operation candidates are:

```text
describe_adapter
validate_plan
execute_plan
```

They represent three distinct interoperability needs: compatibility/capability discovery, advisory preflight, and authoritative execution. Phase 0 does not freeze the exact wire spelling; later protocol schema work owns that detail.

No separate operations are created for Core target selection, capability interpretation, backend realization normalization, semantic effect comparison, or lifecycle classification.

## Boundary examples

### Valid alternative backend schedule

```text
DAG: A and B independent
canonical representation: A, B
backend schedule: B, A
```

This is permitted when dependencies and reporting are preserved.

### Invalid canonical-order overconstraint

A protocol field stating `backend_must_execute_in_canonical_array_order: true` is invalid because it turns a deterministic representation rule into an unnecessary physical scheduling constraint.

### Valid opaque provenance

```text
backend_artifact_ref = "moose:job/12345"
```

is permitted as opaque evidence if no canonical identity/equality rule depends on its backend syntax.

### Invalid backend-native semantic leakage

A canonical protocol payload containing a vendor `MooseProblem*`, COMSOL model node structure, solver-native object graph, or equivalent typed backend object as the semantic subject is invalid.

## Executable counterexample contract

`crates/sol-core-model/tests/architecture_counterexamples.rs` validates a compact boundary-design fixture model. The golden fixture is accepted only when:

- the public operation set is the minimal three-candidate set;
- Public Contract payloads are reused rather than duplicated;
- backend-native structures do not become semantic payloads;
- opaque provenance is not semantic identity;
- canonical ordering does not constrain independent physical scheduling;
- conceptual responsibilities are not exposed one-for-one as remote methods.

Counterexample fixtures independently violate each rule so CI demonstrates that the architecture guard rejects them.
