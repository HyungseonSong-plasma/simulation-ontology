# M0.2 Public Contract Surface Inventory

**Status:** Phase 0 implementation record  
**Milestone:** M0.2 Canonical Public Contract 0.1  
**Issue:** #29  
**Date:** 2026-08-21

## Purpose

This inventory classifies the M0.1 repository surfaces that are relevant to Canonical Public Contract 0.1. The classification is intentionally about **semantic/public-contract responsibility**, not whether a Rust item is currently declared `pub`.

A current Rust type is not normative merely because it is public. Conversely, a semantic concept may be part of Public Contract 0.1 even when the current Rust representation remains internal and a dedicated public DTO must be introduced later.

## Classification vocabulary

- **Public Contract 0.1 concept** — externally meaningful canonical data/semantics that M0.2 must expose through an intentional language-neutral DTO/JSON boundary.
- **Internal implementation** — Rust/runtime representation that may change without defining Public Contract compatibility.
- **Deferred / excluded from 0.1** — useful concept or implementation surface that does not need to be part of Public Contract 0.1.
- **Missing public DTO** — required Public Contract concept whose dedicated DTO does not yet exist in M0.1.

## Canonical identity boundary

Canonical identity semantics are externally meaningful, but the Rust resolver types are not the public contract.

Public DTOs SHOULD carry canonical references in language-neutral scalar form such as:

```json
{
  "source": "thermal.energy_conservation",
  "target": "scope.main_domain"
}
```

The internal `CanonicalId` / `Namespace` types may parse, normalize, index, or validate those values. Public Contract compatibility therefore depends on the normative string/reference semantics, not on Rust fields or constructors.

## Model-facing boundary

The current M0.1 `Simulation` JSON is the closest existing external semantic representation and is therefore the baseline input evidence for M0.2. M0.2 must not simply declare `sol-core-model` Rust serialization to be the permanent contract. Phase 1 introduces an independent Public Contract 0.1 identity and evolution rules, and later phases place the supported DTOs behind an intentional public facade.

The existing `ontology_version` value remains ontology metadata. It is not the Public Contract version and must not be overloaded to serve that role.

## Validation boundary

M0.1 exposes resolver/evaluator failures mainly as Rust enums and CLI strings. Those are insufficient as a language-neutral public contract.

Public Contract 0.1 therefore requires new canonical DTOs:

```text
ValidationReport
  -> diagnostics[]
  -> validity / summary information as explicitly defined in Phase 2

Diagnostic
  -> stable machine code
  -> severity / category as defined by the contract
  -> semantic subject/reference where applicable
  -> human-readable detail
```

`ResolveError` and `ConstraintViolation` remain implementation inputs to diagnostic construction rather than becoming public enum layouts.

## Mapping / planning / evaluation boundary

M0.1 contains the semantic concepts needed for later public DTOs, but several current Rust representations are deliberately unsuitable as direct public JSON contracts:

- `MappingPlan` stores actions in a private `BTreeMap`;
- `PlanAction` dependencies use a Rust `BTreeSet`;
- effect/evaluation types are not serialized;
- mapping claims embed internal `CanonicalId` values;
- target resolution currently depends directly on MockAdapter implementation types.

Phase 3 must define canonical language-neutral DTOs preserving the M0.1 semantics without preserving these internal storage or dependency choices.

## Current CLI boundary

Current CLI golden strings are useful regression tests, but they are not the Public Contract 0.1 machine representation.

Examples such as:

```text
VALIDATION PASS
ontology_version=0.1
model=model.thermal_reference
...
```

and:

```text
MAPPING PLAN PASS
target=mock
adapter=mock.thermal
...
```

must be treated as current human-readable formatting unless a future CLI contract explicitly adopts a machine mode based on canonical DTOs. Phase 6 owns that integration.

## Public-contract dependency rule

A future canonical public-contract data/schema crate must not depend directly on incidental implementation crates such as:

```text
sol-core-identity
sol-core-qrc
sol-core-mapping
sol-core-effect
sol-core-plan
sol-core-evaluation
sol-target-resolver
sol-mock-adapter
sol-cli
```

The public DTO/schema layer should remain language-neutral in shape and independent from internal Rust crate decomposition. Conversion/orchestration code may depend on both the public contract and internal runtime crates, but that dependency direction must not make internal crate layout normative.

An architecture counterexample test is added in Phase 0 to enforce this rule for fixtures and automatically check `crates/sol-public-contract/Cargo.toml` if/when that crate is introduced.

## Deferred questions and Phase ownership

No unresolved question found in this inventory requires reopening semantic architecture before Phase 0 can close. The remaining choices are already assigned to later accepted M0.2 phases:

- Public Contract version envelope, unknown optional-field rules, enum evolution, normalization/equality -> **Phase 1 #30**.
- `ValidationReport` and `Diagnostic` exact canonical shapes -> **Phase 2 #31**.
- `MappingClaim`, `MappingPlan`, `BackendTarget`, `RealizationEffect`, `EvaluationResult` exact canonical shapes -> **Phase 3 #32**.
- JSON Schema layout and golden fixtures -> **Phase 4 #33**.
- structural/semantic compatibility harness -> **Phase 5 #34**.
- intentional Rust facade and CLI machine-facing integration -> **Phase 6 #35**.

If a later phase attempts to make an internal Rust type/crate layout normative, or discovers that preserving M0.1 meaning requires a semantic change, Operator must escalate to Manager `meeting` rather than silently changing this classification.

## Phase 0 conclusion

The M0.1 repository has enough semantic material to proceed with Public Contract 0.1, but the current `pub` Rust API is **not** itself the external contract. M0.2 should build an explicit DTO/schema/facade layer around the public concepts identified above while keeping resolver, evaluator, storage, MockAdapter, and CLI-formatting details internal.
