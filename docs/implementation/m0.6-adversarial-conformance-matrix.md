# M0.6 Adversarial Conformance Matrix

**Status:** Phase 3 implementation record  
**Date:** 2026-08-22  
**Milestone:** M0.6 Adapter Conformance Tooling  
**Parent tracker:** #81  
**Phase:** #85  
**Depends on:** completed Phase 2 #84

## Purpose

Phase 3 extends the external-process conformance runner from the positive fixture path into
reusable adversarial Protocol/Public Contract cases. The goal is not to invent new failure
semantics. It is to prove that published valid-negative behavior, logical ProtocolFailure,
transport/harness failure, and actual adapter semantic non-conformance remain distinct when
observed through an external adapter command.

The production API lives in `sol-adapter-conformance-fixtures` as
`PublishedAdversarialFixtureSuite`. Adapter-specific process configuration is supplied by
the caller for each scenario. The reference MockAdapter `--profile` strings and the local
test adversary commands are development controls only; they are not Protocol fields,
semantic identities, or stable conformance CLI syntax.

## Classification boundary

Phase 3 preserves the Phase 0 result algebra exactly:

```text
published expectation observed
    -> Conformant

published expectation contradicted by a validly observed adapter response
    -> NonConformant

fixture / process / transport / decoding / runner failure
    -> HarnessFailure
```

A `ProtocolFailure` is a logical Adapter Protocol result. When a particular adversarial
case expects that published failure and the observed category/code/detail/side-effect
evidence matches, the case is `Conformant`. The mere presence of a ProtocolFailure is not
an adapter conformance failure.

Transport response loss does not establish an adapter semantic result. It therefore
remains `HarnessFailure` / aggregate `NotEstablished` rather than being relabeled as
`NonConformant` or `ProtocolFailure`.

## Reusable scenario set

`PublishedAdversarialScenario` provides deterministic case identities for the following
published behavior classes:

### Compatibility and preflight

- missing compatibility evidence at bootstrap;
- target mismatch;
- missing required capability;
- unsupported plan action;
- adapter prerequisite rejection;
- transient backend unavailability.

For target and capability counterexamples the suite derives an undeclared value from the
bootstrapped `AdapterDescription` instead of assuming the adapter is MockAdapter. This
keeps the case reusable against an external adapter project.

### Execution and state

- partial execution;
- unsupported realization;
- execution unavailability;
- authoritative execute-time rejection;
- dependency-preserving alternate ordering;
- dependency-preserving parallel independent scheduling;
- already-realized state;
- partial prior execution;
- unresolved prerequisite.

Where a versioned published response fixture exists, the suite compares the external
observation against that canonical fixture and also runs `ExecutePlanResponse::validate_against`
for request-relative invariants.

### ProtocolFailure

- invalid `validate_plan` request failure;
- operational `validate_plan` failure;
- execute failure with `side_effects=none`;
- ambiguous execute failure with `side_effects=may_have_occurred`.

Expected failures are loaded from the published Adapter Protocol 0.1 fixtures and checked
with the operation-specific side-effect rules.

### Failure / replay boundary

The matrix includes execute response loss as a transport-boundary observation. The
M0.5 recovery rule remains authoritative:

```text
execute response lost
    -> side effects conservatively may have occurred
    -> transport must not automatically replay execute_plan
```

Phase 3 does not add retry, replay, idempotency-key, or deduplication authority.

## Semantic non-conformance probes

Three test-only external responder modes prove that the runner can distinguish a parsable
Protocol response from a semantically conforming one:

1. dependency/scheduling violation;
2. aggregate realization-effect mismatch;
3. opaque provenance reference reused as semantic identity.

The responder first creates a locally well-shaped execution response, then changes only a
request-relative invariant. Because `ExecutePlanResponse::from_json` checks local shape and
`validate_against(request)` checks plan-relative semantics, the response crosses the
transport boundary successfully but is classified `NonConformant` by the conformance
runner.

This distinction is important:

```text
malformed/undecodable wire result
    -> HarnessFailure(ResultDecoding or TransportExchange)

parsable result that violates published request-relative semantics
    -> NonConformant
```

The test adversary is not a second reference adapter and is never a production dependency
of the fixture runner.

## Determinism and external-project reuse

Each scenario has a fixed in-memory case ID and Phase 0 `ConformanceScope`. Reports use the
Phase 0 deterministic sort and duplicate-ID rejection. External projects can provide their
own executable command/configuration for a scenario without linking that adapter into Core.

The case IDs are typed runner evidence only in M0.6. Their strings do not stabilize a shell
command, serialized JSON schema, exit code, or package name. Phase 4/5 may build authoring
and external-CI guidance on top of this typed boundary; any normative machine-output or CLI
contract still requires the explicit public-interface review already recorded by Phase 0.

## Backend correctness exclusion

Adversarial conformance still tests only the published SOL interoperability contract. It
does not establish the correctness of a solver equation, discretization, mesh, material,
nonlinear convergence, vendor runtime, or physical/numerical result. The Phase 0 report
continues to expose `BackendValidationScope::NotAssessedByConformance`.

## Rejected counterexamples

The following implications remain invalid and are executable documentation constraints:

```text
expected ProtocolFailure -> adapter non-conformance
transport failure -> ProtocolFailure
execute response loss -> automatic replay
opaque provenance reference -> semantic identity
adversarial case id -> stable CLI spelling
conformance matrix -> solver-native physical correctness
valid negative preflight -> SOL lifecycle state
MockAdapter profile name -> Protocol semantic identity
```

## Phase 4 handoff

Phase 4 may use the positive and adversarial suite to build a minimal external-adapter
project skeleton and authoring guide. The guide must explain how an adapter project supplies
its own executable command/configuration for the scenarios, runs the suite locally/CI, and
performs separate solver-native validation.

Phase 4 must not turn reference test profile names into a normative adapter interface, and
must not imply that Protocol conformance replaces backend physical or numerical validation.
