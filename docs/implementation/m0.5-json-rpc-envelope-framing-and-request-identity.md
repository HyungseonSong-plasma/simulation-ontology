# M0.5 JSON-RPC Envelope, Framing, and Request Identity

**Status:** Phase 1 executable transport profile
**Date:** 2026-08-21
**Milestone:** M0.5 — JSON-RPC / stdio Transport
**Parent tracker:** #74
**Phase:** #76
**Depends on:** Phase 0 #75 / PR #96

## Purpose

This profile carries the Phase 0 method mapping over deterministic JSON-RPC 2.0 objects and local process stdio while preserving published Adapter Protocol 0.1 payload meaning. JSON-RPC request IDs, envelopes, framing, and error objects remain transport metadata; they are not SOL or Adapter Protocol semantic data.

The baseline is the JSON-RPC 2.0 Specification. M0.5 deliberately selects a smaller local single-call profile where the base specification permits transport-specific policy.

## Local JSON-RPC 2.0 profile

Every request and response is one JSON object with `jsonrpc` exactly `"2.0"`. Member names and method names are case-sensitive. Unknown top-level envelope members are rejected so transport metadata cannot silently acquire semantic meaning.

Batch arrays are not part of this local profile. A batch value receives one `Invalid Request` response with `id: null`; it is never treated as an implicit operation ordering or transaction boundary.

Notifications are not dispatched. A syntactically valid object without `id` produces no response and invokes no Adapter Protocol operation. In particular, notification form cannot execute `execute_plan` without an answer.

## Request envelope

Canonical transport emission sorts JSON object keys and uses compact JSON. The three allowed request shapes are:

```json
{"id":1,"jsonrpc":"2.0","method":"describe_adapter"}
{"id":2,"jsonrpc":"2.0","method":"validate_plan","params":{"...":"canonical ValidatePlanRequest"}}
{"id":3,"jsonrpc":"2.0","method":"execute_plan","params":{"...":"canonical ExecutePlanRequest"}}
```

The exact method names remain those fixed by Phase 0:

| Method | `params` rule |
|---|---|
| `describe_adapter` | absent |
| `validate_plan` | one JSON object containing the Protocol request |
| `execute_plan` | one JSON object containing the Protocol request |

Positional arrays, `null`, missing plan-operation params, and params supplied to `describe_adapter` are `Invalid params` transport errors. Once a known method yields the required params object, structural or semantic validation of the nested object belongs to Adapter Protocol and may produce `ProtocolFailure` in the result channel.

## Request identity and correlation

The local profile accepts JSON number IDs only when they are unsigned integers in `0..=9007199254740991`, the interoperable JSON safe-integer range. String, `null`, negative, fractional, and larger IDs are invalid request envelopes.

The supplied generator starts at `1`, increases by one, never wraps, and reports exhaustion after the maximum safe ID. Servers echo the accepted ID unchanged. Clients correlate a response only when its non-null ID equals the outstanding request ID exactly.

An ID is only correlation metadata. It is never copied into params or result payloads and it does not identify a plan, provenance record, canonical entity, adapter process, or session. Reuse of an ID carries no idempotency, deduplication, retry, replay, or resume authority.

## Result envelope

Successful Adapter Protocol results and `ProtocolFailure` are both valid JSON-RPC results. A transport-owned tag distinguishes them without using SOL lifecycle terms:

```json
{"id":2,"jsonrpc":"2.0","result":{"kind":"protocol_success","payload":{"...":"canonical success DTO"}}}
{"id":2,"jsonrpc":"2.0","result":{"kind":"protocol_failure","payload":{"...":"canonical ProtocolFailure"}}}
```

The nested `payload` object is canonical Protocol 0.1 data. The transport does not inject the JSON-RPC ID, method, process, framing, retry, or session fields into it. Decoding `protocol_failure` validates the nested object using the published `ProtocolFailure` model and the mapped logical operation.

The tag is transport classification only; it is not PASS/FAIL/BLOCKED/INDETERMINATE lifecycle state.

## Error envelope

Transport rejection uses the JSON-RPC `error` member and never a `ProtocolFailure` payload. Phase 1 emits the standard codes below with stable messages and no `data` member:

| Code | Message | Phase 1 use | Response ID |
|---:|---|---|---|
| `-32700` | `Parse error` | Complete UTF-8 frame is not valid JSON | `null` |
| `-32600` | `Invalid Request` | Wrong root/envelope/version/ID, extra envelope field, or batch | accepted safe ID when recoverable; otherwise `null` |
| `-32601` | `Method not found` | Exact Phase 0 method lookup fails | echoed request ID |
| `-32602` | `Invalid params` | Method cannot yield its required Protocol object | echoed request ID |

Every response contains exactly one of `result` or `error`. Error responses may contain `id: null` only when no valid correlation ID is available. A null-ID response cannot be correlated to an outstanding request.

Process spawn, broken pipe, EOF, crash, abnormal exit, timeout, and non-protocol output evidence remain Phase 2/3 work; they are not assigned ad hoc JSON-RPC or Protocol failure meanings here.

## stdio framing

The local process transport uses one compact JSON-RPC object per UTF-8 line:

- canonical emission terminates every object with one LF byte (`0x0A`);
- CRLF input is accepted and normalized by removing the CR immediately before LF;
- reads may split one frame or contain several frames; the incremental decoder preserves boundaries;
- JSON string newlines are escaped by JSON serialization and therefore do not create frames;
- blank/whitespace-only lines and invalid UTF-8 are framing errors;
- EOF with buffered bytes but no LF is an unterminated-frame error;
- a complete UTF-8 frame that is malformed JSON reaches JSON-RPC decoding and produces `-32700`.

Framing errors that prevent a complete JSON-RPC object have no request ID. Their caller-visible process/transport evidence is defined in Phase 3, not converted into Protocol failure or SOL lifecycle state.

## Canonical payload pass-through proof

Executable tests wrap the published `validate_plan` request fixture as `params`, serialize and decode the envelope, compare the nested JSON value for equality, and reparse it through `ValidatePlanRequest`. Separate tests prove request IDs remain at the envelope root and both Protocol success and `ProtocolFailure` remain under `result`.

Canonical pass-through means the nested Protocol JSON value and its published meaning are preserved. It does not require preserving insignificant input whitespace or object-member order; transport emission uses deterministic compact canonical JSON.

## Rejected counterexamples

```text
request ID -> Protocol payload
request ID -> SOL semantic or provenance identity
same request ID -> retry or replay authority
notification -> execute without an answer
ProtocolFailure -> JSON-RPC error
JSON-RPC error -> ProtocolFailure
batch -> implicit operation ordering
framing/EOF -> SOL lifecycle state
network transport -> Phase 1 scope
```

## Phase handoff

Phase 2 #77 may connect this pure envelope/framing layer to a local adapter subprocess. It may allocate IDs, write canonical LF frames, incrementally decode stdout frames, dispatch only `RequestDisposition::Dispatch`, and correlate response IDs.

Phase 2 must not redefine Protocol payloads, dispatch notifications, infer lifecycle state from process state, introduce automatic replay/retry, or add network transport. Detailed process/transport error evidence remains Phase 3 and ambiguous execution/reconnect safety remains Phase 4.
