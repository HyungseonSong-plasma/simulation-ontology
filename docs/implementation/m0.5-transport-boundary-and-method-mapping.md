# M0.5 Transport Boundary and Method Mapping

**Status:** Phase 0 implementation boundary  
**Date:** 2026-08-21  
**Milestone:** M0.5 — JSON-RPC / stdio Transport  
**Parent tracker:** #74  
**Phase:** #75

## Purpose

This boundary fixes how the published transport-independent Adapter Protocol 0.1 operations map onto the M0.5 JSON-RPC/stdin-stdout transport without redefining Protocol DTOs, failures, idempotency, lifecycle meaning, or canonical identity.

Phase 0 defines ownership, exact wire method names, payload pass-through, and the failure-channel boundary. It does not implement JSON-RPC envelopes, request-ID rules, stream framing, subprocess lifecycle, reconnect, retry, or replay.

## Authority and ownership

| Concern | Owner | Phase 0 rule |
|---|---|---|
| Adapter Protocol operation and DTO meaning | `sol-adapter-protocol` / published Protocol 0.1 | Transport consumes unchanged meaning |
| Wire method names and operation dispatch | `sol-adapter-transport` | Exact closed mapping below |
| JSON-RPC envelope, request ID, and framing | M0.5 transport | Transport metadata remains outside Protocol payloads |
| Protocol success or `ProtocolFailure` | Adapter Protocol operation result | Carried through the JSON-RPC result channel |
| Malformed JSON-RPC/envelope or unknown method | Transport | JSON-RPC error channel, never `ProtocolFailure` |
| Process/session state | Transport | Never Adapter Protocol state or SOL lifecycle state |
| SOL lifecycle evaluation | Core semantic evaluation | Never inferred directly from transport outcome |
| Backend-native execution | Adapter implementation | Never canonical Protocol or transport identity |

Dependency direction is one way:

```text
sol-adapter-transport
        |
        v
sol-adapter-protocol
        |
        v
sol-public-contract
```

`sol-adapter-protocol` must not depend on `sol-adapter-transport`. This keeps the published protocol reusable across in-process and future transport implementations.

## Exact method mapping

The M0.5 local transport accepts exactly these case-sensitive method names:

| Published logical operation | JSON-RPC method | Protocol request payload | Protocol success payload |
|---|---|---|---|
| `describe_adapter` | `describe_adapter` | none; `params` is absent | `AdapterDescription` |
| `validate_plan` | `validate_plan` | canonical `ValidatePlanRequest` object | canonical `ValidatePlanResponse` |
| `execute_plan` | `execute_plan` | canonical `ExecutePlanRequest` object | canonical `ExecutePlanResponse` |

Aliases, namespaced variants, case variants, and whitespace variants are unknown methods. Adding or renaming a wire method is a transport compatibility decision; it does not silently rename the published logical operation.

The executable mapping lives in `sol-adapter-transport::AdapterTransportMethod`.

## Canonical payload pass-through

For `validate_plan` and `execute_plan`, the extracted JSON-RPC parameter object is the Protocol request object. Transport must not inject correlation IDs, method names, envelope fields, retry metadata, process identifiers, or framing data into that object.

The transport performs this sequence:

```text
JSON-RPC envelope validation
  -> exact method lookup
  -> transport metadata separation
  -> Protocol request parse + normalize
  -> logical operation dispatch
  -> Protocol success DTO | ProtocolFailure
  -> transport-owned result wrapper
```

The nested Protocol success or failure object remains its canonical Protocol 0.1 representation. Phase 1 defines the exact transport-owned tagged result wrapper without changing the nested payload.

A known method with an extracted object that fails published Protocol structural or semantic validation produces the published invalid-request `ProtocolFailure`. A malformed JSON-RPC envelope, positional/wrong-shaped transport parameters that cannot yield the required Protocol object, or an unknown method is a transport rejection and uses the JSON-RPC error channel.

## ProtocolFailure versus transport error

`ProtocolFailure` is a valid outcome of a dispatched Adapter Protocol operation. It must be carried in the JSON-RPC result channel so it remains distinguishable from transport failure.

The JSON-RPC error channel is reserved for failures that prevent dispatch of a valid logical operation, including:

- malformed JSON;
- invalid JSON-RPC envelope/version;
- invalid request-ID representation;
- unknown method;
- missing, positional, or wrong-shaped transport parameters;
- framing failure before a complete request is available.

Process loss and I/O failure may prevent any response envelope; Phase 3 defines their caller-visible transport evidence. They never become `ProtocolFailure` merely because an operation was in flight.

Phase 1 owns exact JSON-RPC result/error object shapes and error numbers. Phase 0 fixes only the ownership and channel classification above.

## Request identity boundary

A JSON-RPC request ID is transport correlation metadata only.

It is not:

- canonical SOL identity;
- Adapter Protocol request identity;
- plan identity;
- provenance identity;
- an idempotency key;
- a replay, deduplication, resume, or retry token.

The request ID is removed before Protocol DTO parsing and is not passed to the adapter operation. Reusing an ID cannot authorize reissuing `execute_plan`.

## Rejected counterexamples

The following interpretations are rejected and executable guards must continue to reject them:

```text
ProtocolFailure -> JSON-RPC error
JSON-RPC error -> ProtocolFailure
request ID -> Protocol payload
request ID -> canonical or provenance identity
same request ID -> replay or dedup authority
transport/process outcome -> SOL lifecycle state
unknown method -> ProtocolFailure
malformed envelope -> Protocol invalid-request payload
network transport -> M0.5 scope
```

## Phase handoff

Phase 1 #76 may implement deterministic JSON-RPC 2.0 envelopes, request correlation, and stdio framing using the exact mapping and ownership boundary above.

Phase 1 must not:

- add or rename logical operations;
- redefine published request/response/`ProtocolFailure` meaning;
- pass request IDs into Protocol payloads;
- use JSON-RPC errors for valid Protocol outcomes;
- introduce replay authority;
- add network/gRPC scope.

Process lifecycle remains Phase 2, error propagation Phase 3, replay/reconnect safety Phase 4, and in-process/subprocess parity plus the milestone exit audit Phase 5.
