# M0.5 Replay, Reconnect, and Ambiguous Execution Safety

**Status:** Phase 4 executable recovery profile
**Date:** 2026-08-22
**Milestone:** M0.5 — JSON-RPC / stdio Transport
**Parent tracker:** #74
**Phase:** #79
**Depends on:** Phase 3 #78 / PR #99

## Purpose

This profile defines what a caller may do after a response-loss or session-loss boundary without silently redefining Adapter Protocol 0.1 idempotency. Reconnect is explicit creation of a new bootstrapped transport session. It never continues the old session and never carries an unacknowledged operation into the new process.

## Explicit reconnect boundary

A faulted session accepts no further operation. The caller may explicitly create a new `AdapterProcessSession`, which always:

1. spawns a new child process;
2. creates new stdin/stdout/stderr ownership;
3. starts a new transport request-ID sequence;
4. performs a fresh `describe_adapter` readiness bootstrap;
5. exposes no pending request from the previous session.

The new process and new request IDs are transport identities only. They do not prove continuity, deduplication, prior completion, or a new canonical semantic identity.

## Operation-specific response-loss policy

`response_loss_recovery` exposes a deterministic `ResponseLossRecovery` for the operation whose valid correlated response was not obtained.

| Operation | Conservative side-effect evidence | Transport replay disposition | Caller rule |
|---|---|---|---|
| `describe_adapter` | `none` | `CallerMayReissueDescription` | a new session performs a fresh bootstrap |
| `validate_plan` | `none` | `CallerMayReissueEquivalentValidation` | caller may reissue only the same normalized request under equivalent relevant adapter state/evidence |
| `execute_plan` | `may_have_occurred` | `TransportMustNotReplayExecution` | transport stops; an explicit higher-level evidence/decision is required before any new execute attempt |

The validation rule is state-dependent idempotency, not generic retry permission. Changed capability, availability, precondition, descriptor, or other relevant evidence means the validation context is not equivalent.

For execution:

```text
no valid ExecutePlanResponse
AND no ProtocolFailure proving a normal logical failure result
=> execution side effects may have occurred
=> transport must not replay
```

The caller receives the Phase 3 operation error and separate process-exit/stderr evidence. No `ExecutePlanResponse`, ProtocolFailure, lifecycle state, or replay authorization is synthesized.

## ProtocolFailure side-effect evidence

A valid `ProtocolFailure` remains a Protocol result and preserves its published `side_effects` field exactly:

- `none` is evidence that operation side effects did not occur;
- `may_have_occurred` is the conservative absence of that guarantee.

Neither value is an automatic transport replay directive. `protocol_failure_authorizes_automatic_replay` is therefore false for every ProtocolFailure. A higher layer may use valid evidence to make a separately authorized decision, but the stdio transport never resubmits the request itself.

## Executable loss cases

The solver-independent fault peer and integration tests prove:

- a lost description response prevents readiness; the caller must open a fresh session and bootstrap again;
- a lost validation response faults the session; only an explicit caller call reissues equivalent validation on a replacement session;
- a lost execution response faults the session, records `may_have_occurred`, and opens a replacement session without replaying execution;
- an observer replacement process receives only its bootstrap before clean shutdown;
- execute ProtocolFailures with both `side_effects=none` and `side_effects=may_have_occurred` survive transport unchanged and authorize no automatic replay.

## Rejected counterexamples

```text
response absence -> no side effects
same canonical execute request -> replay-safe
side_effects=none -> automatic retry authority
side_effects=may_have_occurred -> synthesized INDETERMINATE
new process -> continuation of the prior session
new request ID -> a new semantic operation identity
successful reconnect -> proof the prior execute did not occur
validate_plan idempotency -> unconditional replay under changed state
adapter package version -> stronger execute idempotency
```

The recovery source contains no idempotency key, resume token, deduplication token, generic retryable flag, or safe-to-retry flag. Adding portable replay authority would require an explicit versioned Protocol extension and conformance evidence.

## Phase handoff

Phase 5 #80 must prove in-process/subprocess parity while retaining this operation-specific recovery boundary. Its Validator audit must treat lost execution responses as ambiguous and must reject any test harness behavior that blindly resubmits `execute_plan`.
