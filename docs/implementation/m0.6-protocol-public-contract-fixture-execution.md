# M0.6 Protocol / Public Contract Fixture Execution

**Status:** Phase 2 implementation record  
**Date:** 2026-08-22  
**Milestone:** M0.6 Adapter Conformance Tooling  
**Parent tracker:** #81  
**Phase:** #84  
**Depends on:** completed Phase 1 #83

## Purpose

Phase 2 executes the published Adapter Protocol 0.1 positive fixture baseline against an
external adapter command through the Phase 1 invocation harness. It turns the previously
published contract material into reusable per-case conformance evidence without creating a
second representation of Protocol or Public Contract semantics.

The production fixture runner lives in `sol-adapter-conformance-fixtures`. It depends on
the Phase 0 result model, the Phase 1 external-process harness, and the published Adapter
Protocol types. It does not depend on MockAdapter or a solver runtime. MockAdapter remains
a development-only reference external command for executable proof.

## Published fixture source

The positive suite consumes the versioned material under:

```text
fixtures/adapter-protocol/0.1/
```

The Phase 2 baseline uses:

- `dual-compatible-description.json`;
- `validate-plan-accepted-request.json`;
- `validate-plan-accepted-response.json`;
- `execute-plan-thermal-request.json`;
- `execute-plan-exact-response.json`.

The fixture directory is supplied at runtime, so the same published directory may be
copied into an external project without recompiling or linking an adapter implementation
into Core.

## Validation layers

Phase 2 deliberately preserves two complementary validation layers instead of adding a
new JSON Schema engine to the Rust fixture runner.

### Publication schema gate

The existing required CI scripts remain the authority for structural validation of the
published Draft 2020-12 artifacts:

```text
scripts/validate_public_contract_schemas.py
scripts/validate_adapter_protocol_schemas.py
```

Those gates validate the published schema/fixture corpus and remain part of Rust Core CI.
Phase 2 does not duplicate their schema documents or silently replace them with a new
runner-local schema dialect.

### Runtime canonical payload gate

The fixture runner reads the published JSON and decodes it through the existing canonical
DTO parsers:

- `AdapterDescription::from_json`;
- `ValidatePlanRequest::from_json`;
- `ValidatePlanResponse::from_json`;
- `ExecutePlanRequest::from_json`;
- `ExecutePlanResponse::from_json` plus request-relative `validate_against`.

The request parsers already revalidate the reused Public Contract `BackendTargetDto` and
`MappingPlanDto` payloads through their canonical normalization paths. The runner also
requires those reused payloads to produce canonical Public Contract JSON before adapter
invocation.

This means the executable path consumes the published versioned artifacts and the same
canonical semantic types that define Protocol/Public Contract behavior; it does not
translate them into a second fixture-specific DTO family.

## External execution flow

The positive suite is:

```text
published versioned fixtures
        |
        v
canonical Protocol/Public Contract decode
        |
        v
Phase 1 external adapter harness
        |
        +--> describe_adapter + dual compatibility
        +--> validate_plan
        +--> execute_plan
        |
        v
canonical observation comparison
        |
        v
Phase 0 ConformanceCaseRecord / ConformanceReport
```

The reference `describe_adapter` comparison intentionally ignores adapter implementation
version. Adapter implementation version is an independent version axis and cannot establish
Protocol or Public Contract compatibility. The positive reference case compares the
published compatibility declarations and target/capability semantics instead.

`validate_plan` must match the published accepted response. `execute_plan` must both match
the published exact response and satisfy the request-relative execution invariants.

## Deterministic evidence

The reference positive run produces stable case identifiers for:

- published Adapter Protocol fixture decoding;
- reused Public Contract canonical payload validation;
- `describe_adapter` behavior;
- Adapter Protocol compatibility;
- Public Contract compatibility;
- `validate_plan` behavior;
- `execute_plan` behavior.

Phase 0 `ConformanceReport` sorts case identifiers and supplies the aggregate determination.
The exact serialized report format, CLI spelling, exit-code policy, and fixture-discovery
convention are still provisional and are not stabilized by these in-memory case IDs.

## Failure boundary

A fixture file that cannot be read or decoded produces
`HarnessFailureKind::FixtureLoad`. The aggregate result is therefore `NotEstablished` unless
another observed adapter violation exists. Missing or malformed runner input does not
accuse an adapter of non-conformance.

A logical `ProtocolFailure` remains a Protocol observation. In this Phase 2 *positive*
fixture matrix it contradicts the positive expected operation and therefore yields a
non-conformant case; later adversarial Phase 3 cases may instead expect a specific
`ProtocolFailure` and classify it as conformant.

Invocation/transport failures continue to map through the Phase 1 harness failure channel.
They do not become `ProtocolFailure` or SOL lifecycle states.

## Backend correctness exclusion

The aggregate report retains
`BackendValidationScope::NotAssessedByConformance`. A completely conformant positive
Protocol/Public Contract fixture run establishes interoperability evidence only. It does
not validate solver equations, discretization, mesh, material data, convergence, numerical
accuracy, or physical correctness.

## Public-interface status

Phase 2 adds reusable Rust fixture execution, not a finalized user-facing runner contract.
The following remain outside stabilization until explicit public-interface review:

- standalone conformance executable name;
- command/option spelling;
- exit codes;
- serialized report schema;
- stdout/stderr rendering;
- default fixture search/discovery paths;
- package/distribution naming promises.

## Rejected counterexamples

The following implications are invalid:

```text
published fixture copy -> new semantic representation
fixture load failure -> adapter non-conformance
positive suite conformance -> solver-native physical correctness
adapter implementation version -> Protocol/Public Contract compatibility
runner case id -> stable CLI/output contract
canonical DTO parse -> replacement of published JSON Schema CI gate
```

## Phase 3 handoff

Phase 3 may extend the same runner/result boundary with the published adversarial corpus:
incompatible/missing support, preflight rejection/unavailability, execution degradation,
partial and unavailable behavior, dependency/scheduling violations, ProtocolFailure,
ambiguous execute response loss, provenance leakage, and transport counterexamples.

The Phase 3 matrix must preserve the Phase 2 separation between expected logical Protocol
failure, observed adapter non-conformance, and harness/transport failure. It must not gain
automatic retry/replay authority and must not redefine Adapter Protocol 0.1 or Public
Contract 0.1 meaning.
