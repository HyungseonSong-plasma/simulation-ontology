# M0.4 MockAdapter Conformance Boundary

**Status:** Phase 0 implementation baseline  
**Parent:** #65  
**Phase:** #66

## Purpose

M0.4 promotes MockAdapter into the Core repository's executable reference implementation of the published Adapter Protocol 0.1 baseline. This document fixes the local implementation boundary without changing Public Contract 0.1 or Adapter Protocol 0.1 semantics.

## Existing M0.1 API classification

The pre-M0.4 `sol-mock-adapter` surface predates the published Adapter Protocol and is therefore classified as Rust-local legacy/reference-helper behavior:

- `Adapter` trait — legacy/internal Rust helper, not a public protocol interface;
- `AdapterCapability` — legacy Core-side helper, not canonical capability DTO identity;
- `PlanAcceptance` — legacy helper, not `ValidatePlanResponse`;
- `FailureInjection` — test/reference control, never protocol payload;
- `SimulatedRealization` — legacy helper combining Core realization and lifecycle classification; not protocol output;
- `MockAdapter::capabilities`, `assess_plan`, `realize` — legacy/internal convenience behavior.

These APIs may remain during M0.4 for additive compatibility and existing tests. They do not define Adapter Protocol conformance.

## Protocol-facing authority

The M0.4 conformance path must consume and produce the published language-neutral DTOs owned by:

- `sol-adapter-protocol` for adapter description, preflight, execution, and protocol failure semantics;
- `sol-public-contract` for BackendTarget, MappingPlan, Diagnostic, RealizationEffect, and other shared canonical semantic payloads.

A protocol-facing MockAdapter implementation must not create duplicate local semantic equivalents of those DTOs.

## Source boundary

Protocol-facing MockAdapter implementation will live under:

```text
crates/sol-mock-adapter/src/protocol.rs
```

This source boundary is intentionally separate from the existing M0.1 helper implementation in `lib.rs`. The protocol module may add inherent behavior to `MockAdapter` or protocol-local implementation helpers, but it does not create a new normative Rust protocol trait. Adapter Protocol 0.1 remains language-neutral and responsibility-driven.

## Lifecycle boundary

The existing legacy `realize` helper currently computes Core `EvaluationStatus`. That remains a Rust-local legacy convenience only.

Protocol-facing MockAdapter operations must not return, serialize, or infer SOL lifecycle states. They produce Adapter Protocol/Public Contract evidence only. Lifecycle classification remains Core responsibility after suitable canonical semantic evidence exists.

## Transport boundary

M0.4 conformance is in-process and transport-independent. The protocol-facing MockAdapter module must not define process framing, request IDs, subprocess lifecycle, network behavior, automatic replay, or transport retry policy. Those remain M0.5 work.

M0.4 may use direct Rust method calls in tests because the goal is reference semantic/protocol behavior, not a public Rust FFI or transport API.

## Conformance-test boundary

M0.4 may add Core-local test helpers that exercise MockAdapter against published Protocol 0.1 fixtures. These helpers are not the productized reusable external-adapter runner; that belongs to M0.6.

Conformance authority is the published Protocol 0.1 contract plus executable fixtures/counterexamples, not incidental Rust trait shape.

## Additive compatibility strategy

Phase 0 does not remove or rename the existing M0.1 helper API. New protocol-facing behavior is additive.

If later M0.4 implementation discovers that correct conformance requires breaking a supported Rust facade or changing published Protocol 0.1 meaning, Operator must stop and route the issue to Manager review.

## Executable architecture guards

Phase 0 adds source-level guards that require the dedicated protocol-facing module and reject obvious lifecycle/transport/solver-dependency leakage from that path.

The guards are intentionally narrow: they protect the reference-conformance boundary while allowing legacy helper implementation to remain during additive migration.

## Phase 1 handoff

Phase 1 may now implement deterministic `describe_adapter` behavior in `protocol.rs` using published Adapter Protocol 0.1 DTOs, while preserving the legacy M0.1 API separately.
