## 2. Accepted runtime boundary

M0.7 preserves three distinct concepts:

```text
BackendTarget
  = canonical solver-independent target semantics

AdapterRegistration
  = Core-local locator and invocation configuration

AdapterInstance
  = live operational process/session state

BackendTarget != AdapterRegistration != AdapterInstance
```

Registration paths, arguments, working directories, registration IDs, instance IDs, PIDs, JSON-RPC IDs, process stderr, and exit status are runtime evidence only. They are not canonical SOL semantic identity.

## 3. Accepted end-to-end runtime path

M0.7 proves the solver-neutral runtime path:

```text
explicit local AdapterRegistration
        |
        v
external adapter process launch
        |
        v
mandatory describe_adapter bootstrap
        |
        v
live Adapter Protocol + Public Contract compatibility evidence
+ target/capability declarations
        |
        v
AdapterRuntimeProjection
        |
        v
canonical BackendTarget + required capabilities
        |
        v
deterministic adapter selection
        |
        v
validate_plan / execute_plan dispatch
        |
        v
explicit shutdown
```

Selection outcomes are explicit:

```text
0 eligible  -> NoCompatibleCandidate
1 eligible  -> Selected
2+ eligible -> Ambiguous(sorted candidates)
```

The runtime never silently chooses an arbitrary adapter among multiple eligible candidates.

## 5. Compatibility and transport invariants

M0.7 preserves the existing published boundaries rather than redefining them.

- Live compatibility requires both Adapter Protocol and Public Contract compatibility evidence.
- Static registration metadata and adapter package version do not establish interoperability.
- Missing compatibility evidence remains not established rather than silently compatible.
- `validate_plan` remains advisory and side-effect free.
- `execute_plan` remains authoritative and non-idempotent by default.
- Ambiguous lost `execute_plan` response preserves `MayHaveOccurred` and `TransportMustNotReplayExecution`.
- Reconnect creates a fresh process/session rather than assuming prior-session continuity.
- Transport/process failures remain distinct from logical Protocol failure and from SOL lifecycle classifications.

## 6. M0.8 coexistence

M0.8 separately published Public Contract 0.2 and Adapter Protocol 0.2 with the canonical `RealizationSpec` boundary.

M0.7 does **not** claim Adapter Protocol/Public Contract 0.2 runtime operation support merely because 0.2 DTOs and schemas exist in the repository. The accepted M0.7 runtime integration proof remains on the explicit 0.1 runtime pair.

A successor runtime milestone must explicitly integrate 0.2 operation dispatch and compatibility evidence before SOL Core may claim end-to-end 0.2 runtime support.

## 7. Real-adapter boundary

M0.7 proves generic Core runtime interoperability mechanics. It does not prove solver-native realization correctness, numerical convergence, or physical validity.

Real adapters remain separate repositories and own:

- backend-native mapping;
- solver API/artifact generation;
- solver-specific regression tests;
- physical/numerical V&V where applicable.

No MOOSE, COMSOL, Ansys, or other solver runtime dependency is introduced into Core by M0.7.

## 8. Product surfaces intentionally not stabilized

M0.7 does not stabilize:

- automatic adapter discovery;
- adapter package/manifest standards;
- marketplace/download/install flows;
- signing/trust/update contracts;
- stable GUI plugin UX;
- stable TypeScript/Python SDK ABI;
- solver-specific configuration editors;
- remote/network transport.

These remain later product decisions built on the proven runtime boundary.
