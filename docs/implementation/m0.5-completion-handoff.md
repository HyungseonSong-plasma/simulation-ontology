## Result

M0.5 carries the unchanged published Adapter Protocol 0.1 operation payloads over a
deterministic local JSON-RPC 2.0/stdin-stdout process boundary.

The completed transport behavior includes:

- exact JSON-RPC method mapping for `describe_adapter`, `validate_plan`, and
  `execute_plan`;
- incremental LF/CRLF stdio framing and standard JSON-RPC rejection behavior;
- numeric request IDs used only for transport correlation;
- explicit Protocol success/failure result tagging without conflating JSON-RPC errors;
- a generic local subprocess session with piped stdin/stdout/stderr ownership;
- mandatory `describe_adapter` bootstrap before a session becomes ready;
- typed validate/execute calls that decode back into published Protocol 0.1 DTOs;
- stable transport/process error categories for malformed responses, EOF, timeout,
  broken pipe, abnormal exit, stderr, framing, correlation, and payload failures;
- opaque raw stderr and separate process-exit evidence;
- explicit fresh-session reconnect with no hidden request carryover;
- description and equivalent validation reissue only through explicit caller action;
- conservative `may_have_occurred` evidence and no transport replay after lost execute
  responses;
- deterministic CLI-only MockAdapter profiles for every existing reference state; and
- canonical in-process/subprocess parity across positive, negative, adversarial, failure,
  scheduling, prior-execution, and response-loss cases.

## Preserved boundaries

1. Adapter Protocol 0.1 and Public Contract 0.1 meanings and version axes remain
   unchanged.
2. JSON-RPC IDs and process/session identity are transport correlation only, never SOL
   semantic identity.
3. ProtocolFailure remains distinct from JSON-RPC, framing, process, and invocation
   errors.
4. Process/session/error states do not become SOL lifecycle or evaluation states.
5. `validate_plan` remains advisory and state-dependent; `execute_plan` remains
   authoritative and non-idempotent by default.
6. Response loss does not authorize blind execute replay, even when a new process starts
   successfully.
7. stderr and backend references remain opaque evidence rather than semantic authority.
8. M0.5 introduces no network/gRPC or real solver/backend runtime dependency.

## Handoff to M0.6

M0.6 productizes reusable Core-side tooling that lets external adapter projects
demonstrate published Adapter Protocol/Public Contract conformance without claiming
solver-native physical or numerical correctness.

Parent #81 and Phase issues #82–#87 are already accepted. Phase 0 #82 is the next eligible
implementation unit after this completion update merges.

M0.6 must preserve these constraints:

- conformance result semantics remain distinct from SOL lifecycle semantics;
- adapter logical failures remain distinct from harness/transport failures;
- external adapters are invoked through the published process transport instead of linked
  into Core;
- positive and adversarial tests consume versioned published fixtures and schemas;
- exact CLI spelling and output contracts require explicit public-interface review before
  stabilization;
- no solver-specific dependency enters Core solely for conformance tooling; and
- protocol conformance never claims backend-native physical correctness.
